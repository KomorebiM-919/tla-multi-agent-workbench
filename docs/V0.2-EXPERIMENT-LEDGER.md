## 3. 更正：旧数字 84 与 100 的口径漏项

旧文档写过两个合计：

- `docs/V0.2-B1-MATRIX.md` §8.2：**84 / 84**（只含 `repair3/run` 20、`repair3/run2` 1、`repair3/run3` 37、`repair4/run` 26）。
- 同文件 §10：**100 / 100**（84 再加 `repair5/run` 16）。

两者都**没有**把 B-1 的四次运行（`resume #1` 2、`resume #2` 1、`two-teams` 5、`cancel` 1，共 **9**）算进去，
也都**不可能**包含 closure 的四次（**21**，发生在 100 之后）。

因此：

- 用户问的"新四次共 21 次放行是否已包含在既有 100 中" —— **否**；
- 同理，旧 84/100 也不是"全部历史"，它们缺了 B-1 的 9 次；
- 按日志去重复算的合计是 **130 放行 / 130 到达**，不是 100，也不是 100+21=121。

这次更正不修改旧段落，只在旧段落追加指向本文档的说明；原始日志一行未动。

## 4. 完整性口径（为什么大多数是 INCOMPLETE）

- `INCOMPLETE` 不等于"运行失败"，而是"账本缺一段证据"：
  - B-1 四次与 `repair3/run2` 用的假服务版本**没有分阶段事件**（没有 `arrived`/`responded` 分开写），
    所以"响应/没答完"只能是 `unknown`；
  - `repair3/run` 的上游比放行多 1（21 vs 20），原因是两次 `listening`/`closed` 写进同一文件、
    上游在闸门关闭后 44 秒还在收尾，**差额仍未查清**；
  - `repair5/run` 有 3 条请求没有结束事件（旧假服务的错误分支不写 `responded`），因此 3 条 `没有答完`。
- `COMPLETE` 只表示"这条运行的四段证据齐了"，不表示"模型调用成功"：
  `closure/run2`、`run3` 各有 1 条错误响应（引擎 `NO_PROGRESS`），`run4` 有 1 条错误响应（宿主拒绝写文件）。

## 5. 复算方法

```bash
# 单次运行
node tools/recompute-ledger.mjs --json <run-dir>

# 全部运行（本地脚本，不在仓库内，因为它知道 .scratch 目录布局）
node tests/.scratch/v02-stage2/ledger-index.mjs
```

`ledger-index.mjs` 会逐条调用 `measureRun()` 并打印同样的字段；本文档的表格就是它的输出，
手工抄录之外的数字没有被"整理"过。
