# V0.2 最小真实集成实验计划（三阶段，尚未授权）

本文件是**申请**，不是已完成的操作记录。写这份计划时本轮仍是离线状态：没有安装任何插件、没有安装依赖、没有调用任何模型、没有配对手机、没有开放端口、没有 Push。

目的：把"能不能真的跑一次多模型协作"拆成三个阶段，每个阶段都能单独批准、单独停止、单独回滚；并且明确每阶段**能证明什么、不能证明什么**。

---

## 0. 先划清四条界线

1. **"两个不同模型" ≠ "两个不同 provider"**
   - 两个不同模型：同一 provider 下的两个 model id（例如 `deepseek-official/deepseek-flash` 与 `deepseek-official/deepseek-v4-pro`）。这只能证明"多模型可被分别指定"。
   - 两个不同 provider：两个不同的 provider 条目（例如 `deepseek-official` 与另一个厂商的 provider）。这才能证明"跨 provider"。
   - 只配了 `deepseek-official` 一条渠道时，**不得**把多模型协作表述成跨 provider 协作。计划里的 `totals.distinctModels` 与 `totals.distinctProviders` 已经分开计数，`totals.coverage.multiProvider` 只有真的两个 provider 才为真。
2. **"计费渠道" ≠ "provider"**
   `deepseek-official`（API key 计费）与 `deepseek-account`（账户额度计费）是同一厂商的两条计费渠道，价格可能不同、余额来源不同。价格快照按 `provider/model/channel` 三元组索引：渠道不同不能共用单价，也不能互相 fallback。
3. **"预算" ≠ "付款能力"**
   计划里的分配是账面额度，不是供应商余额、不是已扣款、不是跨供应商资金划拨。本仓库没有任何充值、付款或资金划拨能力。
4. **"模拟通过" ≠ "宿主验收通过"**
   夹具里模拟的 `agent/request` 瀑布与 agent-loop 重试循环，只证明拦截逻辑自洽。真实宿主里的插件生命周期、安装形态、会话恢复、并发与中止语义，必须在隔离 profile 里实测。

## 2. 阶段 1：安装验证（0 次模型调用）

**授权范围**：向一个**新建的隔离 profile** 安装上述包，并做"插件能被加载、工具能出现、团队能建能删"的验证。不连真实模型端点。

验收条件（全部满足才算通过）：

1. 安装后 `dsh` 能启动且现有 profile 不受影响（隔离 profile 用独立 `DSH_HOME`/profile 目录，具体参数待安装前确认）。
2. `@nanmicoder/dsh-agent-teams` 出现在插件列表，版本号确实是 `0.1.23`（不是 `0.1.24-rc.1`）。
3. 公开工具集与已核对清单一致（14 个工具：`create`、`edit_plan`、`approve`、`add_member`、`remove_member`、`create_task`、`reassign_task`、`claim_task`、`update_task`、`amend_task`、`send_message`、`status`、`resume`、`delete`）。
4. 建一个**空计划**团队（`plan.tasks` 为空或只有一个不派工的任务）、读 `status`、再 `delete`；全过程 0 次模型请求。
5. 卸载/回滚后，状态目录被清理或能被明确列出并手动删除。

**不能证明**：能跑真实协作、成员能启动、模型能响应、计数能拦住。

停止条件（任一触发即停并报告）：安装失败、版本不是 `0.1.23`、出现意料外的网络访问、需要升级宿主、需要改动现有 profile。

回滚：卸载插件 → 删除隔离 profile 的状态目录 → 确认现用 profile 的插件列表与安装前一致。

## 3. 阶段 2：零调用宿主验证（拦截语义，仍不付费）

**目的**：验证 `orchestration/interceptors/prelaunch-budget.mjs` 的假设在**真实宿主**里成立。冻结证据（只读核对）已经给出预期语义：

- `agent/request` 瀑布在 `llm.prepareCall()` 之前触发（`dsh-agent-loop/lib/index.js:1179` → `:1189`）；
- 监听器抛错 → 请求不发出，错误冒到 turn 级 catch（`:1008`），该 turn 以 error 结束；
- 重试是 `continue` 回到 `while` 顶部（`:1134` → `:1050`），所以每次重试都会再次进入瀑布；
- 未打标签的监听器在根上下文注册即可看到所有 agent（`dsh-scope/README.md:42`、`:77`）。

阶段 2 要用真实宿主验证这四条，且**不产生任何付费模型调用**。可行做法（按优先级）：

1. **限制器置零**：安装一个只做拦截的本地测试插件，`modelRequests: 0` → 任何 agent 请求都应在发起前被拒。若观察不到任何出站请求、且 turn 以错误结束，则该接缝"发起前"语义成立。
2. **本地不可达端点**：把隔离 profile 的 provider `baseURL` 指向 `127.0.0.1:<未监听端口>`，`modelRequests: N` → 允许的前 N 次会以连接失败告终（不产生模型调用、不产生费用），第 N+1 次应被拦截器在**发起前**拒绝。通过"连接失败次数 = N"来证明放行次数准确，通过"第 N+1 次没有连接尝试"证明拦截在发送前。
3. **重试语义**：制造一次可重试的错误（连接失败通常是可重试的），观察重试是否再次进入 `agent/request`、是否再预占一次。
4. **并发**：同时发起多个会话/成员，验证计数不重复、不丢。

需要额外授权的具体动作：安装本地测试插件到隔离 profile、把隔离 profile 的 provider 指向 `127.0.0.1`（本机回环，不是外网）。**不需要**：真实凭据、真实模型、公网端口。

验收条件：上面四条都在真实宿主里被观察到；任意一条不成立，就把对应能力标为"未验证"，并停止依赖它的后续阶段。

**不能证明**：真实模型会按预算停止（模型侧没有配额概念）、token 用量能被限制。

## 4. 阶段 3：付费协作实验（需用户单独决定）

只有阶段 1、2 都通过才申请。当前**不申请无人值守或自动返工的付费实验**。

### 4.1 计数单位（五个，分开命名，不可互相替代）

| 单位 | 谁能拦 | 现状 |
| --- | --- | --- |
| 成员创建次数 | 无接缝 | 不发起模型请求，未计数 |
| 代理启动次数 | 仅 V0.1 `workflow-script` 后端（`task.maxAgentCalls`，默认 8，启动前检查） | agent-teams 后端**没有**这个接缝；`maxMembers`（8）不是调用上限 |
| 模型请求次数 | 宿主 `agent/request` 瀑布（拦截器） | 逻辑已在夹具验证，**真实宿主未验证** |
| 重试次数 | 同上（重试会重新进入瀑布） | 语义已由只读代码确认，真实宿主未验证 |
| token 用量 | 无 | 只能在运行后按会话日志复算 |

**明确撤回**此前两种说法：
- "手工观察第 6 次 spawn 就形成调用上限" —— 观察不是拦截；
- "3M tokens 时立即停止" —— 没有 token 级的发起前拦截。

### 4.2 最小实验参数（申请值）

| 项 | 申请值 | 理由 |
| --- | --- | --- |
| 插件 | `@nanmicoder/dsh-agent-teams@0.1.23` | 稳定版，peer 已含 `0.2.0-rc.2`；若拒绝，则改用 `0.1.24-rc.1` 并接受预发布风险 |
| 宿主 | 现用 DSH **0.2.0-rc.2**，不升级 | 避免把"插件问题"和"宿主升级问题"混在一起 |
| profile | 新建隔离 profile，不动现用 profile | 可回滚 |
| 计费渠道 | `deepseek-official`（API key 渠道，单价见宿主目录） | 已有官方目录价；`deepseek-account` 没有公布单价，无法估算 |
| 模型 | `deepseek-official/deepseek-flash`、`deepseek-official/deepseek-v4-pro` | 均在宿主默认目录中列出；两者是**两个模型、同一 provider**，不足以证明跨 provider |
| 团队规模 | 3 成员（owner + 1 worker + 1 reviewer） | 最少可验证"逐成员不同模型" |
| 轮次上限 | 每个成员 1 次派工，不允许自动返工 | 自动返工会放大调用 |
| 模型请求硬上限 | `modelRequests: 20` | 3 成员 × 少量轮次 + 余量；由拦截器在发起前拒绝第 21 次 |
| 账面预算 | 建议 USD 1.00 以内（按宿主目录价：flash 0.3/1.2、v4-pro 1.32/3.96 每百万 token） | 20 次请求 × 2 万输入 / 4 千输出 ≈ 远低于 1 美元 |
| 人工监督 | **必须**：全程有人盯着 `status` 与拦截器计数 | 没有启动前 agent 计数，不能无人值守 |
| 停止条件 | 拦截器拒绝、或出现任何非预期报错、或人工判断偏离任务，立即停止并 `delete` 团队 | — |
| 回滚 | 停团队 → 卸载插件 → 删除隔离 profile → 核对现用 profile 未变 | — |

### 4.3 阶段 3 的验收口径

- 只有"真实模型返回了符合要求的结果 + 拦截器计数与实际请求数一致 + 预算未超"三条同时成立，才算"一次真实协作跑通"。
- 只跑通一次不等于稳定；V0.1 验收条件不因此被整体重判，V0.2 的验收条件（真实模型调用）也只是**首次满足**，不是"平台完成"。
