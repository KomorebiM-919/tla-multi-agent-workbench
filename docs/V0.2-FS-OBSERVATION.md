# V0.2 专项：读后写（read-before-write）到底发生了什么

closure 第四次运行（`closure/run4`，2026-10-18）里，队员写 `src/note.txt` 被宿主拒绝：

```
Error: cannot modify "…\closure\project\src\note.txt": file has not been read — read the file, then retry
```

当时的判断是"读后写契约挡住了写入"。这份文档更正它：**那次写之前根本没有读**，
宿主的拒绝是正确的；错在夹具漏了那一步。下面给出证据、宿主契约和离线检查。

## 1. 证据：note.txt 从未被读

`closure/run4` 的 14 条请求体逐条检查（脱敏副本见 `tests/fixtures/repair-protocol/`）：

| 请求 | 工具数 | 最后一条 `tool_use` | 曾读过 note.txt |
| --- | --- | --- | --- |
| 001–008 | 26/38 | `agent_teams_create` / `…status` / `…claim_task` | 否 |
| 009 | 26 | `read(src/sum.mjs)` | 否 |
| 010 | 38 | `agent_teams_status` | 否 |
| **011** | 26 | **`write(src/note.txt)`** | **否** |
| 012–014 | 38 | `agent_teams_status` | 否 |

请求 011 的历史是：`claim t1` → `update in_progress` → `read src/sum.mjs` → **直接** `write src/note.txt`。
中间没有 `read src/note.txt`，也没有对应的 `tool_result`。所以宿主看到的是"这个会话没观察过该文件"，
按契约只能拒绝。

根因是策略规则：当时那条规则在"读完 `sum.mjs`"之后直接回了 `write note.txt`，而不是先回 `read note.txt`。
修好后的规则（`tests/fixtures/repair-loop-policy.v2.json`）会先回 `read note.txt`，再回 `write note.txt`；
`tests/v02-repair-loop.test.mjs` 的 30 步预演与 `tests/v02-repair-protocol.test.mjs` 的回放都覆盖了这个顺序。

## 2. 宿主契约（只读抽取，未改安装目录）

来源：`app.asar` 内的 `@deepseek-ai/dsh-fs-observation-policy`、`dsh-fs-local`、`dsh-tool-fs`
（DSH `0.2.0-rc.2` 随包文件）。抽取脚本：`tests/.scratch/v02-review/asar.py`（只读）。

| 维度 | 宿主行为 | 依据 |
| --- | --- | --- |
| 谁算"同一次观察" | 观察状态按 `actor.agent.session` 隔离，弱引用持有 | `dsh-fs-observation-policy/lib/index.js:29-31, 36-42` |
| 目标身份 | `targetKey = realpath(displayPath)`；缺失目标用 `realpath(最近存在祖先)+后缀` | `dsh-fs-local/lib/index.js:169-211`（175、196 行） |
| 文件版本 | `` `${dev}:${ino}:${size}:${mtimeNs}:${ctimeNs}` `` | `dsh-fs-local/lib/index.js:146` |
| 写一个"没读过的已存在文件" | 意图是 `createIfAbsent`，已存在 → 失败，工具统一渲染成 `cannot modify "…": file has not been read — read the file, then retry` | `…observation-policy/lib/index.js:51-58`；`dsh-tool-fs/lib/index.js:475-480` |
| 读后被改动 | 版本不匹配 → `FS_STALE_VERSION`，提示 `— re-read the file, then retry` | 同上 |
| 读一个不存在的路径 | 记录 `absent`；之后可以受控创建，但并发创建不会被静默覆盖 | `…observation-policy/lib/index.js:64-75` |
| 会话恢复 | 观察状态**不持久化**，恢复后必须重新读 | `…observation-policy/README.md`（Lifecycle 段） |
| 没有会话的直接调用 | 可以随便读，但**永远**满足不了受保护的写 | `…observation-policy/lib/index.js:29-31` |

一句话：**同一会话 + 同一 realpath + 同一版本**，三者都满足才允许覆盖。

## 3. 离线检查（`tests/v02-fs-observation.test.mjs`，20 项断言）

模型在 `tests/lib/observation-model.mjs`，明确标注"据宿主源码归纳的契约模型，不是宿主实现"。
覆盖：

1. run4 的真实顺序（读过 `sum.mjs`、直接写 `note.txt`）→ 拒绝，且报错文本与抓到的字符串一致；
2. 补上 `read note.txt` 后同一会话再写 → 允许；
3. 同一文件的多种写法（大小写、`.`、`..`、`./`、`\` 与 `/`）→ 归一到同一个 key，写被允许；
4. 跨会话读 → 不授权（另一个会话仍然 `FS_NOT_OBSERVED`）；
5. 无会话 → 永远 `FS_NOT_OBSERVED`；
6. 读失败 → 不记录任何观察，后续写仍是未观察；
7. 读后文件变化 → `FS_STALE_VERSION`，提示重读；
8. 读缺失 → 记录 `absent`；文件随后出现 → 拒绝覆盖（并发创建保护）；确实不存在 → 受控创建成功。

## 4. 更正与仍然未证明的事

- **更正**：旧结论"读后写契约导致队员写失败"不准确。真实情况是夹具漏了 `read`，
  宿主按契约拒绝了未观察的写；契约本身没有问题。
- **仍未验证**：在**中等完整性令牌**下，队员先读后写能否真的成功写盘。`closure/run4` 只走到
  "未读被拒"，没有产生一次成功的队员写入；`repair5` 与权限预检里的写失败是 ACL/DACL 问题
  （`SetFileSecurityW EACCES`），两者是**不同**的失败，不能互相解释。
- 本文件不改变任何原始日志；它只是把失败链重新对齐。

## 5. 对夹具的约束（写进正式测试）

- 不允许给夹具加"无限重试"或"绕过宿主规则"的规则：写失败只能回读一次（`maxUses` 有上限），
  第二次同样的失败必须终止（`tests/v02-repair-loop.test.mjs` 断言了这一点）。
- 不允许把错误结果解释成完成：`completed` 只能来自全绿测试行。
