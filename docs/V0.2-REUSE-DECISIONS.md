# V0.2 复用决策：六个候选组件的结论与依据

本文记录 V0.2「开源复用与最小接入」阶段对六个候选源码仓库的**只读核对结论**，以及各自在 TLA 中的处置方式。

**本轮性质（必须先读）**：六个仓库都只是**源码参考**。它们没有安装、没有启用、没有做本机兼容性验收，也没有任何真实模型调用。本文的每条"已核实"都指"在该 commit 的源码/文档里读到了这条证据"，不等于"在本机验证过它能工作"。第三方文档里的安装命令**不是**用户授权，本轮一律未执行。

## 1. dsh-agent-teams：适配调用（团队执行后端候选）

**决策：适配调用，不是直接依赖，也不是复制。** 本阶段只实现"兼容性探测 + 计划翻译"，执行适配明确标记为未实现。

已核实（`6768de2`）：

- 公开导出只有五个名字：`name`、`inject`、`Config`、`usageSectionText`、`apply`（`lib/index.js:40-118`）。**没有**公开的状态读取 API，也没有调度器导出。
- `apply(ctx, config)` 需要 `tools`、`llm`、`subagents`、`systemPrompt`、`agents` 五个服务，Web 路由还需要 `webServer`/`workspaceRegistry`。**没有**文档化的"被其它程序嵌入"的接口——因此 TLA 不能假设自己可以像调用库一样调用它。
- 14 个工具（`src/tools.ts`）：`create`(:918)、`edit_plan`(:1124)、`approve`(:1248)、`add_member`(:1280)、`remove_member`(:1384)、`create_task`(:1443)、`reassign_task`(:1601)、`claim_task`(:1732)、`update_task`(:1833)、`amend_task`(:2059)、`send_message`(:2140)、`status`(:2275)、`resume`(:2420)、`delete`(:2472)。
- 逐成员 `provider`/`model` 是**真实存在**的：`create` 的 `plan.members[]` 支持 `provider`、`model`、`reasoning_effort`、`tool_policy`、`fallback`；解析在 `resolveMemberLlmSelection`（`src/members.ts:467-559`），显式 provider 必须配显式 model，且**请求级 model 是用户选择，永不被重新路由**（`:506-508`）。这与"手动指定负责人模型、执行模型"的产品需求一致——这也是它成为首选后端的原因。
- 持久化：`<workspace>/<stateDir>/<teamId>/team.json` + `inbox/<agentKey>.jsonl`（`src/state.ts:4-7`）。并发控制只是**进程内** promise 队列（`src/state.ts:67`，`README.md:197` 明说多进程不协调）。
- **没有模型调用计数器**：全仓只有 `ATOMIC_RENAME_RETRIES = 3` 这个与文件系统重命名有关的常量（`src/state.ts:611`）。限制只有 `maxMembers` 8、`memberMaxDepth` 0、评审轮次（`src/quality-gates.ts:44-47`）。

模型请求的发起位置（决定"能不能拦住每一次调用"）：

| 触发 | 位置 | 是否经过 TLA 可见的同步点 |
| --- | --- | --- |
| 成员创建 | `src/tools.ts:1280` | 不调用模型（纯名单行） |
| 首次派工 | `src/members.ts:945`（`startMember` 内 `agentOptions` :958-964） | 每次 spawn 解析一次调用配置 |
| followup 消息 | `src/members.ts:1002` | 否 |
| 自动修复 | `src/quality-gates.ts:1047` | 否 |
| 停止后 resume | `src/tools.ts:2420` → `kickTeam` | 否 |
| 模型 fallback | `src/members.ts:746-762` | 否 |

结论：**无法承诺"全局模型调用硬上限"**。如果将来接入，只能声明"每次 spawn 解析一次调用配置"，并且必须如实标注 `hardCapApplicable: false`。这正是计划里 `CALL_CAP_PARTIAL` 警告的来源，不得省略。

### 1.1 宿主侧"启动前计数"的可行性（只是方案，未实现）

要让调用次数变成硬上限，闸门必须在**每次模型请求发出之前**、在 TLA 能控制的位置同步拒绝。按可行性从高到低：

| 方案 | 能否拦住每一次 | 代价 / 风险 | 本轮结论 |
| --- | --- | --- | --- |
| A. TLA 自建宿主插件，挂 `agent/request` 瀑布流最前面，计数并在超限时抛错 | 很可能可以：这是 llm 服务层的统一入口，followup / 自动修复 / resume / fallback 的请求都应经过它 | 需要 TLA 自己的插件（当前不存在）、需要在 agent-teams 之后注册、要证明抛错的失败形态是"干净停止"而不是半途状态；**必须真实调用才能验证** | 唯一值得做隔离实验的方案 |
| B. 依赖插件自身的 `maxMembers` / 评审轮次 | 不能 | —— | 成员数量 ≠ 调用次数，明确不用 |
| C. 在提示词里写"最多调用 N 次" | 不能 | 模型可以不遵守 | 明确不用，不能冒充拦截 |
| D. 事后解析 `team.json` / `inbox/*.jsonl` 对账 | 不能（事后） | 只能"花了多少"，不能"挡住下一次" | 不接受作为上限口径 |
| E. 网络层 / 沙箱出口拦截 | 不能按团队区分 | 宿主进程共享网络，无法归属某次调用 | 不采用 |

因此本阶段的写法是：`callAccounting.hardCapApplicable: false`、`readiness.budgetProtection: "allocation-plan-only"`、`missingForExecution` 里记 `CALL_CAP_NOT_ENFORCEABLE`，并把方案 A 留作"需要授权 + 真实调用"的最小隔离实验（见本轮报告的下轮授权请求）。

最小隔离实验的边界（供批准时核对，未执行）：临时 workspace + 2 成员团队；1 次派工 + 1 次 followup，预期计数 2；第 3 次应被拒绝；硬上限设成极低值；每步记录调用前后计数与插件状态；出现"拒绝后状态损坏"即停止并回滚。

### 1.2 "两个 provider 实测"与"必须安装 0.1.24-rc.1"是两件事

- **两个 provider 实测**检验的是：逐成员 `provider`/`model` 真的按配置执行（不串号、不被请求级覆盖），以及不同计费渠道（DSH 账户 / API key / 订阅）不会被同名模型混用。它只需要一个能跑通的 agent-teams 版本。
- **安装固定发行版**是另一件事：本阶段核对到的只是克隆 HEAD 的版本号 `0.1.24-rc.1`（预发布）。**没有联网核实 npm 上是否还有同系列的非预发布版本**，也没有核实 `dsh plugin` 是否支持指定版本安装与干净卸载。接入前应先用只读查询（如 `npm view <pkg> versions`，需联网授权）确认可用版本，优先选无预发布后缀者；`0.1.24-rc.1` 不是默认唯一选择。
- 宿主兼容：`compatibility.json` 的 `supportedHosts` 含 `0.2.0-rc.2`（track `legacy`），`0.2.1-rc.1` 是 recommended。本机 Desktop 是 0.2.0-rc.2。
- 安装可回滚性：需要证明"装得上、停得掉、删得净"（插件目录、`$DSH_HOME` 下的状态、会话事件登记）。本轮只读，未验证。

未验证事项（接入前必须逐条验证，不能假设）：

1. 宿主 0.2.0-rc.1 **不在** `compatibility.json` 的 supportedHosts 里（只有 0.2.0-rc.2 与 0.2.1-rc.1 等）。本机 DSH Desktop 是 0.2.0-rc.2，track 为 `legacy`。
2. `agent-teams/*` 会话事件受 `KNOWN_SESSION_EVENT_TYPES` 门禁（`src/events.ts:45-54`）：宿主没登记就静默丢弃，外部无法依赖这些事件做审计。
3. 没有 member-start / model-call 事件。
4. `agent/request` 只是一次请求的钩子，不是"启动前"的全局闸门。
5. `0.2.1-rc.1` 的兼容性证据本轮未复跑。

## 2. dsh-model-router：暂缓（仅作参考实现）

**决策：不启用，只作"宿主扩展现有长什么样"的参考。**

已核实（`d5205b3`）：

- 它的钩子不是"设置某角色的模型"，而是在 `agent/request` 瀑布流上以前置方式重写请求（`src/index.ts:264-301`），**会覆盖用户在 UI/会话里选择的模型**。
- 只有两个全局角色 `planner`/`executor`（默认 `deepseek-official/deepseek-flash`，`mode: "strict"`，`enabled: true`），没有逐成员固定。
- 没有模型 fallback，只有 `escalateOnError` 调高 reasoning effort（默认关闭）。
- `cordis.patch.yml:45-52` 会整行替换目标配置行，重置 `llm-deepseek` 的模型目录。

结论：与"逐成员手动固定、手动选择优先"直接冲突。若要逐成员路由，应当用 agent-teams 自带的成员级 `provider`/`model`，**不要**同时引入两个会争抢模型选择的机制。

## 3. portkey-models：直接依赖（仅数据，离线）

**决策：作为价格数据源直接依赖，但只在离线导入时读取，不进运行时。**

已核实（`72e1084`）：

- 数据布局：`pricing/{provider}.json`，provider 取文件名，model 是顶层键；价格在 `pricing_config.pay_as_you_go.{request_token,response_token,cache_write_input_token,cache_read_input_token}.price`。
- 单位：`README.md:63` 明确 "Prices are in cents per token, not dollars"；换算 `$/1M = price × 10_000`。
- **没有** `source`、`updated_at`、`effective_date`、峰谷字段。DeepSeek 条目没有 `custom_pricing`，因此峰谷价一律记为未知。
- `currency` 只在 `default` 条目出现；`azure-ai.json`/`deepbricks.json`/`deepinfra.json` 有重复顶层键。
- `general/` 只有 `type.primary`（chat/embedding/…）与 `params`，**没有**上下文窗口字段。

本轮实际取用的 6 条（离线快照 `orchestration/data/pricing-snapshot.portkey-72e1084.json`，单位为微-分/百万 token）：

| provider | model | 输入 | 输出 | 缓存读 | 备注 |
| --- | --- | --- | --- | --- | --- |
| deepseek | deepseek-v4-pro | 43_500_000 | 87_000_000 | 362_500 | 峰谷未知 |
| deepseek | deepseek-v4-flash | 14_000_000 | 28_000_000 | 280_000 | 峰谷未知 |
| deepseek | deepseek-chat | 14_000_000 | 28_000_000 | 280_000 | 数值与 V2 报价一致，疑似陈旧 |
| deepseek | deepseek-reasoner | 14_000_000 | 28_000_000 | 280_000 | 同上 |
| moonshot | moonshot-v1-8k | 20_000_000 | 200_000_000 | 未知 | 无 cache_read 字段 |
| zhipu | glm-5.2 | 140_000_000 | 440_000_000 | 26_000_000 | 峰谷未知 |

**新鲜度声明**：快照记录的是"从 `72e1084` 的这些文件读到的字节"，仓库本身没有时间戳，因此**无法证明价格是最新的**，也**没有**与供应商官网核对。快照的 `capturedAt` 是采集动作发生的时间，不是价格生效时间。

注意 provider 命名空间差异：DSH 的 provider id 是 `deepseek-official`，portkey 的文件名词干是 `deepseek`。两者不做静默别名——必须在配置里显式写 `pricing.providerAliases`，且计划里会记录实际查价用的 provider 与 `aliased` 标记。别名**只影响查价**，不会改成员真实执行的 `provider`/`model`；计划里两者分开记录。

缓存写也计费：`cache_write_input_token` 会被导入为 `cacheWriteMicroMinorPerMillion`（deepseek 三家本轮都是 0），缺失时该条目标 `cacheWritePricing` 未知，估算按输入价取上界。

### 3.1 价格刷新流程（本轮未执行，需要联网授权）

1. 在 `portkey-models` 克隆里 `git fetch` 并记录新 commit SHA（只读操作，不改本地依赖）。
2. `node tools/import-portkey-pricing.mjs --pricing-dir <克隆>/pricing --commit <新SHA> --captured-at <ISO> --out <新文件>`；导出器会做重复键、币种、单位、整数性校验。
3. 与旧快照逐条 `diff`，人工确认哪些变了；**不自动采用**新价格，也不沿用旧 `capturedAt`。
4. 更新本文档的价格表与"新鲜度声明"，必要时提升 `snapshotId`；旧快照保留，用于复现历史计划。
5. 与供应商官网人工核对至少一个条目——portkey 仓库没有价格生效时间，程序无法判断新旧。
6. 峰谷价：只有出现可靠来源（带字段与时间）才录入，否则继续标 `offPeakPricing` 未知。

## 4. dsh-token-anxiety：参考实现（不启用）

**决策：只参考它的成本展示与峰谷界面，不启用其同步与解释功能。**

已核实（`78c60a4`）：

- 静态价表 `index.js:29-58`（`asOf 2026-08-15`）。
- 价格同步走网页 LLM 解析：`POST /token-anxiety/pricing-sync` → `runLlmJson`（`index.js:1125-1153`，硬编码 `deepseek-v4-flash`）。
- `explain_task` 工具每次调用花 1 次 LLM 调用。
- 固定汇率表 `fx.rates{CNY:7.1,EUR:0.85,BRL:5.4,COP:3137.58}` 与 `CNY_TO_USD = 7.0`。
- 峰谷窗口 `peakWindowsUtc [{1,4},{6,10}]`、`valleyFactor: 0.5`。
- 没有预算强制，也没有"这是估算"的免责声明。

结论：它的价格同步与费用解释**都会调用模型**，本轮禁止。固定汇率与峰谷折扣缺乏依据，不照搬；TLA 的峰谷字段在没有可靠来源时一律标未知。

## 5. dsh-mobile：暂缓（独立通道，待单独授权）

**决策：本轮只审查与准备，不安装、不重启宿主、不开端口、不配隧道。** 详细清单见 `docs/V0.2-MOBILE-CHANNEL.md`。

已核实的要点：

- 兼容表（`README.md:406-408`，插件 0.6.11）声称在 `0.2.0-rc.2` 做过隔离浏览器 CI，同时注明"浏览器检查不代表所有手机内核、第三方插件或公网线路已验收"。
- peer deps 全为 `"*"` 且 optional。
- APK 0.6.5（versionCode 81、tag `android-v0.6.5`、sha256 `41bd476c5ccf90020ecf624844a29886d55060a79533b599e9aa5bf0a1d71844`）。
- 手机加载的是**真实的 DSH Web UI**，能答题审批；`SECURITY.md:55` 明确 "paired device = fully trusted operator、pairing is not a read-only sandbox"。
- **手机 UI 不区分"计划审批"与"宿主操作审批"**：只有 DOM 标记 `[data-question-key]` 与 `[data-plan-review-key]` 不同，通知 kind 只有 `'done' | 'question'`。
- 通知依赖页面存活与 SSE，不是离线推送。

必须由用户本人在手机上实测、本轮无法代做的部分（清单同步写在 `docs/V0.2-MOBILE-CHANNEL.md` §6）：

- Desktop 正确 profile（`web` profile 的插件是否与手机配对的宿主一致）；
- 固定插件 0.6.11 / APK 0.6.5 的实际安装与版本回显；
- 配对撤销：电脑端删除记录后，手机端 SSE 是否立刻 `device-revoked`、旧会话是否失效；
- 后台通知限制：锁屏 / 切后台 / 断 SSE 时会不会漏审批，多久超时；
- 移动网络 allow/deny 实测：仅移动数据（无 LAN）时能否连上，以及用了隧道后**公网可达范围**是否符合预期；
- 回滚：卸载插件 + `dsh plugin --profile web exec dsh-mobile purge --yes` 后，`$DSH_HOME/mobile-access/` 是否清净、宿主是否恢复正常。

## 6. RouteLLM：研究参考（不引入）

**决策：只作为"智能路由如何评估"的研究参考，本阶段不引入任何自动路由。**

已核实（`0b64fda`，2024-08-09）：

- 4 个路由器：`mf`、`sw_ranking` 需要每条 prompt 调用 OpenAI embeddings；`causal_llm` 需要 HF Llama-3-8B checkpoint；`bert` 本地；`random`。
- README 声称"85% 成本 / 95% GPT-4 水平"，但仓库内**没有**价格表与成本计算代码。
- 模型 id 是 2024 年的（有 `deepseek-llm-67b-chat`，没有 v4/flash）。

结论：它在"不调模型"的约束下根本无法运行（embedding 也是模型调用），且强/弱双模型路由不等于五供应商调度器。TLA 本阶段只做**手动配置 + 确定性规则**；智能推荐要等有真实评估数据之后再做。

- 不执行第三方安装脚本，不启用第三方插件，不改宿主配置。
