## 3. 阶段 2：真实宿主上的启动前预算

四个实验都用同一个本地假模型服务（记录每一次收到的 HTTP 请求），拦截器是本地插件
`orchestration/interceptor-plugin/`（`ctx.on('agent/request', listener, {prepend:true})`，
同步预占后 `return next()`；超额抛 `MODEL_REQUEST_BUDGET_EXCEEDED`）。

| 运行 | 上限 | 场景 | 假服务收到的请求 | 预算事件 | 退出码 |
| --- | --- | --- | --- | --- | --- |
| run1 | 3 | 单轮问答 | 1（`toolCount: 38`） | 1 预占，0 拒绝 | 0 |
| run2 | 2 | 单轮内连续工具调用 | **2** | 2 预占，1 拒绝（第 3 次在发起前被拒，服务端无第 3 条） | 1 |
| run2-restart | 2 | 状态文件已用尽后重启 | **0** | 挂载即 `resumeMode: resumed`、`used: 2`，首个请求被拒 | 1 |
| run3 | 4 | `agent_teams_create`（`approval: automatic`，1 成员 + 1 任务） | 4：队长 3 条（`session-…`）+ **成员 1 条**（`toolCount: 26`） | 4 预占，2 拒绝 | 1 |
| run4 | 6 | 同 run3，外加 `agent_teams_send_message` 唤醒成员（followup） | 6：队长 4 条 + **成员 2 条** | 6 预占，2 拒绝 | 1 |
| run5 | 2 | 拦截器监听器抛非预算错误 | **0** | 无预占 | 1 |

要点：

- **额度耗尽 = 零新增发送**：run2/run3/run4 的服务端记录条数与预占数相等，被拒的那次没有任何 HTTP 请求。
- **跨会话覆盖**：run3/run4 里队长会话（`session-…`，`toolCount: 38`）与成员会话（无 `session-` 前缀的 continuable 会话，`toolCount: 26`）共用同一份额度；成员首次派工与 followup 唤醒都计入。
- **重启不重置**：状态文件存在时读回 `used` 继续；读不出来就把额度视为用尽（每个请求都拒）。
- **监听器异常 = fail-closed**：run5 抛错后进程以 1 退出、假服务 0 请求。
- 累计：受控运行里本地假模型请求 **13 次**（1+2+0+4+6+0），真实外部模型调用 **0 次**。
- 全轮（含失败证据）的**去重后**服务端请求总数：**2580 次**——受控 13 次 + 修复前失控重启 2567 次。逐次：run1 1、run2 2、run2-restart（失控）2567、run2-restart（修复后）0、run3 4、run4 6、run5 0。计数来自各运行目录的 `requests.jsonl`（每条 HTTP 请求一行；`listening` 记录已剔除），原始日志未改写。预占（`reserved`）总数 = 13，拒绝（`rejected`）= 5。

### 3.1 负面发现（重要）

1. **插件激活失败只警告，不 fail-closed。** 修复前的版本在"状态文件已存在"时于 `apply()` 抛 `BUDGET_STATE_PRESENT`；宿主打印 `dsh: warning: 1 entry did not activate` 后**继续无预算运行**，实验里该会话对本机假服务发起了 **2567** 次请求（`run2/restart.log`；`requests.jsonl` 共 2570 行，含 1 条 `listening`，可归因到该会话的请求 2567 条，seq 到 2569）才被手工终止。若换成真实端点，这就是一次无上限花费。
   → 现在 `apply()` 永不抛错，改在监听器里 fail-closed；并且**任何"拦截器已生效"的判断都必须同时看挂载事件与服务端计数**，不能只看"装上了"。
2. **拒绝事件原本不落盘**：修复前 `budget-state.json` 的 `rejected` 恒为 0。现在每次拒绝都写状态与事件。
3. `agent_teams` 的 `stateDir` 必须是**相对路径**（给绝对路径会拼成 `...\run3\teams\D:\...\run3\teams\<team>\inbox` 并 ENOENT）。
4. 假服务的脚本步进是进程内全局序号，跨运行不重置；每次实验必须重启服务，否则脚本会错位（本轮踩过一次）。

### 3.2 付费实验的前置阻塞（2026-10-18 追记：已由启动闸门处理；保护强度取决于覆盖率校验）

当前只证明了"**监听器生效时**能拦住请求"，**没有**证明"挂载失败时整体拒绝运行"。宿主对插件激活失败只给 warning，因此存在一条真实路径：拦截器没挂上 → 会话照常跑 → 无人监督时预算形同不存在。付费实验（阶段 3）在这一点解决前**不得授权**。

**追记（同日）**：上述缺口已用"网络层默认拒绝"处理——预算闸门 `orchestration/gate/gate.mjs` 只绑回环、默认拒绝，启动器 `tools/gated-run.mjs` 在启动宿主前校验生效配置的 `baseURL` 指向闸门、读到新鲜挂载心跳才发租约。真实宿主三次运行（插件缺失 / 正常挂载 / 额度耗尽）的上游请求数分别是 0 / 1 / 1。实现、故障矩阵与**未证明项**见 [`V0.2-PRELAUNCH-GATE.md`](V0.2-PRELAUNCH-GATE.md)；下表三个候选判据中，第 1、3 条已落地，第 2 条仍只有夹具级证据。

**再追记（同日，闸门验证轮）**：闸门本身**不足以**构成强制保护。生效配置里存在多个模型 provider 实例（`llm-deepseek`=`deepseek-official`、`llm-deepseek-account`=`deepseek-account`），闸门只在 `baseURL` 被覆写到它的实例上生效；实测把同一 provider 的 `baseURL` 指向另一个回环端点后，宿主直接把请求发给该端点并正常返回（run G），闸门完全看不到。因此启动器新增了**覆盖率校验**（`extractProviderCoverage` + blocker `PROVIDER_NOT_GATED`）：只要有一个 provider 实例未指向闸门就拒绝启动、宿主不启动（run F strict：非闸门端点 0 请求）。同时用"插件完全不参与拒绝"的 run E 证明额度耗尽确实由闸门独立拦下（客户端 2 次、上游严格 1 次）。

**再再追记（同日，独立审查修复轮）**：外部静态审查后把保护从"插件在不在"进一步收到"运行身份 + 配置同源"上。闸门删除全部 HTTP 写控制面（写接口 405、租约只由同进程调用），租约改为显式状态机（永久撤销后不能再发、迟到心跳不复活、撤销不能续期、新租约不复位已用额度）；挂载证明绑定启动器生成的运行级 `runId`（插件每条事件带 `runId`，他 run 事件、坏行、`unmounted` 一律拒绝）；生效配置改为受限 YAML 子集的结构化解析（未知适配器记 `unknown` 并拒绝启动）；探测失败按 spawn/signal/timeout/exit/unreadable/unparseable 分类，必须完整解析才算成功，并逐文件 sha256 比较 patch、比较环境与 runId。真实宿主复验（`round2/`）：正向 `EXIT=0`、两个 provider 实例均 guarded、上游 1 条与插件 `reserved=1` 一致、`runId` 全程一致；不装插件时 `EXIT=3`、`HEARTBEAT_MISSING`、闸门 `MOUNT_PROOF_PROOF_MISSING`、上游 0 新增。真实外部模型调用仍为 0 次。

后续必须验证的启动保护方案（本轮只登记，不实现、不测试）：

| 方案 | 判据 |
| --- | --- |
| 会话启动前的显式闸门 | 未检测到拦截器挂载心跳时，直接拒绝发起会话（而不是先跑起来再说） |
| 心跳双向核对 | 每次运行前读 `mounted` 事件，并在服务端侧确认"请求数 ≤ 预占数" |
| 把"无心跳"视为失败条件 | 启动脚本把"缺少挂载事件"当作非零退出，而不是当成缺省继续 |
