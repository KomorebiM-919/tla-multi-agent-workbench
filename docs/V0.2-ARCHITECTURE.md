# V0.2 最小架构：配置 / 计划 / 执行适配三层

本文描述 V0.2「多模型手动分工 + 预算规划」的最小架构、数据契约与**能力边界**。它描述的是**已实现的离线原型**，不包含真实模型调用。

## 1. 分层

```
┌───────────────────────────────────────────────────────────────┐
│ TLA 自有层（本阶段已实现，全部离线）                          │
│  配置校验  →  价格查询  →  费用估算  →  预算分配  →  计划     │
│  orchestration/config.mjs   pricing.mjs   estimate.mjs        │
│  orchestration/money.mjs    plan.mjs    cli.mjs               │
└───────────────────────────┬───────────────────────────────────┘
                            │ 计划（tla.v02-plan/v1）
┌───────────────────────────▼───────────────────────────────────┐
│ 执行适配层（orchestration/adapters/agent-teams.mjs）          │
│  兼容性探测 → 计划翻译 → 执行（未实现，恒返回 unavailable）   │
└──────┬──────────────────────────────────┬─────────────────────┘
       │                                  │
┌──────▼───────────────┐        ┌─────────▼────────────────────┐
│ workflow-script 后端 │        │ agent-teams 后端（候选）      │
│ 已验证：three-agent- │        │ 未安装、未执行；每次 spawn 才 │
│ mvp；同步调用次数硬顶│        │ 解析一次调用配置，无全局硬上限│
└──────────────────────┘        └──────────────────────────────┘

旁路（不进入执行链）：
  价格快照（离线 JSON，来自 portkey-models@72e1084）
  用量报告（TLA 已有 usage 证据目录，本轮未改动）
  手机通道（独立通道，见 docs/V0.2-MOBILE-CHANNEL.md）
```

三条设计原则：

1. **执行后端可替换，验收/证据/审批/预算门禁留在 TLA。** 换后端不能改变"谁批准、证据在哪、预算谁算"。
2. **不确定就阻断。** 价格未知、币种不符、快照过期、后端不可用、调用上限无法保证——一律变成计划里的 blocker 或 warning，绝不默认成 0 或"应该没问题"。
3. **计划不是运行。** 本阶段所有产物都是计划与翻译结果，`executePlan()` 恒返回 `unavailable`。

## 2. 三个数据契约

### 2.1 运行配置 `tla.v02-run-config/v1`

```json
{
  "schema": "tla.v02-run-config/v1",
  "runId": "v0.2-plan-demo-20261018T000000Z",
  "roles": {
    "lead":   { "provider": "deepseek-official", "model": "deepseek-v4-pro", "reasoningEffort": "high" },
    "worker": { "provider": "deepseek-official", "model": "deepseek-v4-flash" },
    "reviewer": { "provider": "moonshot", "model": "moonshot-v1-8k" }
  },
  "ownerRole": "lead",
  "router": { "enabled": false, "policy": "none" },
  "budget": {
    "currency": "USD",
    "totalMinor": 2500,
    "allocations": [
      { "role": "lead", "basisPoints": 4000 },
      { "role": "worker", "basisPoints": 4000 },
      { "role": "reviewer", "basisPoints": 2000 }
    ]
  },
  "pricing": {
    "snapshotPath": "orchestration/data/pricing-snapshot.portkey-72e1084.json",
    "maxAgeHours": 168,
    "providerAliases": { "deepseek-official": "deepseek" }
  },
  "estimates": {
    "perCall": { "inputTokens": 20000, "outputTokens": 4000, "cacheReadTokens": 8000, "cacheWriteTokens": 0 },
    "calls": { "lead": 2, "worker": 6, "reviewer": 2 },
    "assumptions": { "cachePriceEqualsInput": false }
  },
  "backend": { "kind": "workflow-script", "workflow": "three-agent-mvp", "task": { "...": "..." } }
}
```

校验规则（全部实现并测试）：

- 顶层只允许 `schema`/`runId`/`roles`/`ownerRole`/`router`/`budget`/`pricing`/`estimates`/`backend`；任何其它键（例如想直接写 `readiness`、`executionImplemented`、`budgetProtection`、`limits`）一律 `CONFIG_UNKNOWN_KEY`——**就绪与预算保护只能由计划计算，不能被配置声明**。
- `router.enabled` 必须为 `false`、`policy` 必须为 `none`；其它写法直接 `ROUTER_UNSUPPORTED`。
- 每个角色必须显式写 `provider` 与 `model`（缺一个即 `ROUTE_INCOMPLETE`）。
- 角色的 `selection` 只能是 `manual`；写 `auto` 等即 `SELECTION_UNSUPPORTED`。
- 角色出现 `fallback` 即 `FALLBACK_UNSUPPORTED`（本阶段不允许自动降级）。
- 角色可选 `channel`（计费渠道），写了就必须是非空字符串；空串报 `ROUTE_INVALID`，不允许"空串 = 未知"。
- `ownerRole` 必须存在于 `roles` 中。
- `budget.allocations` 必须覆盖每个角色，且基点之和**恰好** 10000。
- `pricing.providerAliases` 必须是非空字符串映射，且禁止自映射；它**只影响查价**，不改变执行的 provider/model。
- `estimates.assumptions` 只允许 `cachePriceEqualsInput`，值必须是布尔；未知键即 `ESTIMATES_INVALID`。
- 币种只支持 1 主单位 = 100 最小单位的币种（USD/CNY/EUR）；JPY 之类直接拒绝，而不是悄悄按两位小数处理。

### 2.2 价格快照 `tla.pricing-snapshot/v1`

每条价格带 `provider`/`model`/`mode`/`channel`/`prices{input,output,cacheRead,cacheWrite}/provenance/unknownFields`，整份快照带 `snapshotId`、`currency`、`capturedAt`、`source{repository,commit,license,files}`。金额单位是**微-分/百万 token**（整数），不存在浮点价格。

`channel` 是**计费渠道**（同一模型在不同渠道可以有完全不同的单价与扣费方式），条目的唯一键是 `provider/model/channel`。查询时：

- 声明了 `channel` → 只匹配该渠道，匹配不上就是 `PRICE_CHANNEL_MISMATCH`（不会退回"同 model 别的渠道"）；
- 没声明 `channel` 且该 `provider/model` 在快照里只有一个渠道 → 用这一条，但计划会加 `PRICE_CHANNEL_UNSPECIFIED` 警告；
- 没声明 `channel` 且有多条渠道 → `PRICE_AMBIGUOUS_CHANNEL`，不猜。

单价缺失不会被补 0，而是写进该条的 `unknownFields`：`cacheReadPricing`、`cacheWritePricing`、`offPeakPricing`。其中 `offPeakPricing` 是**所有**条目都带——portkey 数据里根本没有峰谷字段（见复用决策文档 §3），所以本阶段的估价一律不含峰谷折扣。数值没有区间、没有币种换算，峰谷与优先级一律按未知处理。

### 2.3 计划 `tla.v02-plan/v1`

成员行是"这次谁用哪个模型、大概花多少、分到多少"的唯一事实来源：

| 字段 | 含义 |
| --- | --- |
| `provider` / `model` | 执行的模型（与配置完全一致，不做覆盖） |
| `channel` | 执行时的计费渠道（未声明为 `null`，不猜测） |
| `selection` / `selectionSource` | 固定为 `manual` / `config (manual)` |
| `isOwner` | 是否负责人角色 |
| `priceStatus` / `priceProvenance` / `priceLookup` | 价格是否已知、来自哪、实际用哪个 provider/model/channel 查的（含 `aliased`） |
| `estimateStatus` / `estimateConfidence` / `assumedFields` | `known`/`partial`/`assumed`/`unknown` 与可信度 |
| `calls` / `estimatedMicroMinor` | 调用次数假设与估算（未知时为 `null`，不是 0） |
| `allocationMicroMinor` / `withinAllocation` | 分配额与是否超分配 |
| `unknownFields` | 该成员自身未确定的项（如 `cacheRead`、`cacheWrite`、`offPeakPricing`） |

顶层还包含 `totals`、`routerGuard{mode:"manual-pinned",autoRoutingEnabled:false,overridable:false}`、`backend`、`hostCatalog`、`callAccounting`、`budgetEnforcement`、`status`、`blockers[]`、`warnings[]`、`limitations[]`、`notProofOf[]`。

**就绪状态拆成六个维度**，任何一项缺失都不得 `status: "ready"`：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| `readiness.configValid` | `true` | 计划只由校验通过的配置生成 |
| `readiness.estimatesAvailable` | `true`/`false` | 所有角色都有可用单价（`known`/`partial`）且能估算 |
| `readiness.estimateConfidence` | `high`/`medium`/`low`/`none` | 全部角色里最差的可信度 |
| `readiness.backendCompatible` | `true`/`false` | 宿主/插件版本/公开导出/注入服务都对得上 |
| `readiness.executionImplemented` | `true`/`false` | TLA 侧真的实现了执行适配（当前只有 `workflow-script` 为真） |
| `readiness.budgetProtection` | `"call-count-hard-cap"` / `"allocation-plan-only"` | 是否有"每次模型启动前"的同步计数闸门 |
| `readiness.hostRouteVerified` | `true`/`false`/`null` | 是否核对过宿主目录；`null` = 没提供目录，没核对 |

`missingForExecution[]` 列出还缺什么（`ESTIMATES_INCOMPLETE`、`BACKEND_UNAVAILABLE`、`BACKEND_EXECUTION_NOT_IMPLEMENTED`、`CALL_CAP_NOT_ENFORCEABLE`、`HOST_ROUTE_UNVERIFIED`），`executable` 当且仅当它为空**且** `blockers` 为空；`status` 由 `executable` 推导。**"插件装了、兼容探测通过"不等于可执行**——这条是复审时发现并修掉的真实缺陷（旧实现会把兼容探测结果直接当成 ready）。

**宿主目录比对**（`--host-catalog`，可选）：用随包只读提取的宿主模型目录核对"这个 provider/model 到底在不在、走哪个计费渠道、目录价与快照价是否一致"。结论写进 `hostCatalog{provided,catalogId,capturedAt,unlistedRoles,channelMismatchRoles,priceConflictRoles,checked[]}`：

- 模型不在目录里 → blocker `HOST_CATALOG_MODEL_UNLISTED` + `missingForExecution` 加 `HOST_ROUTE_UNVERIFIED`（未列出的 id 只会被当文本透传，**不等于**可用）；
- 快照价与目录价**同渠道**却不一致 → blocker `PRICE_DIVERGES_FROM_HOST_CATALOG`（预算依据本身错了）；
- 快照价来自**另一个渠道** → 只警告 `HOST_CATALOG_PRICE_CHANNEL_DIFFERS`（不同渠道的单价不可比）；
- 没提供目录 → `provided: false`，`hostRouteVerified: null`，绝不假装核对过。

## 3. 金额语义（务必区分）

- 预算是**计划上限**，不是付款、不是供应商余额、不是跨平台资金划拨。计划里固定写 `budgetEnforcement: "allocation-plan-only"`。
- 分配用**基点**（整数，总和 10000）+ **最大余数法**，保证各角色分额之和**恰好**等于总额，不需要浮点容差。余数相同时按**声明顺序**补给前面的角色（确定性，换顺序会换到另一角色，但守恒不变）。
- 估算用整数微单位；调用次数与 token 数都是**人工假设**（`config.estimates`），不是历史实测。
- `tokens × 单价 / 100 万` 一律**向上取整**（`divCeil`）：估算是上界，任何非零用量都不会被算成 0，也不会低于按价目计算的理论值。旧实现用 half-up，`costForTokens(1, 1)` 会得到 0。
- 除法中间量在 2^53 附近会静默舍入：`divCeil` 先判断 `numerator > MAX_SAFE_INTEGER - (denominator - 1)` 再相加，`divRoundHalfUp` 对 `2 × magnitude + denominator` 做安全整数检查，越界一律 `MONEY_OVERFLOW`，不返回"看起来对"的错值。
- 缓存价缺失时**不再**用输入价冒充上界：默认把金额记为**未知**（`estimateStatus: "unknown"`、`estimatedMicroMinor: null`），并写进 `unknownFields`（`cacheReadPrice`/`cacheWritePrice`）。理由是没有任何供应商计费依据能把"输入价"折算成"缓存价"。
- 只有配置里显式声明 `estimates.assumptions.cachePriceEqualsInput: true`（用户选择的假设）时，才用输入价代入，并标 `estimateStatus: "assumed"`、`estimateConfidence: "low"`、`assumedFields` 列出被假设的项。这种计划仍然 `blocked`，并带 blocker `ESTIMATES_ASSUMED`——假设不能当"预算内"的证明。
- 有价格但缺**非金额**维度（如峰谷价）时是 `partial` / `medium`：金额按已知单价算，但口径不完整，`withinTotalBudget` 仍然给出（因为金额本身是真实单价算的），同时带 `ESTIMATE_PARTIAL` 警告。
- 没有汇率换算：币种不一致直接阻断，不做跨币种折算。金额刻度目前假设 `1 主单位 = 100 最小单位`，只支持 `USD`/`CNY`/`EUR`，其他币种直接拒绝（`BUDGET_CURRENCY_INVALID` / `PRICING_INVALID`）。

## 4. 调用计数边界（这是本阶段最重要的限制）

先分开五个单位，它们**不能互相替代**：

| 单位 | 谁能拦 | 现状 |
| --- | --- | --- |
| 成员创建次数 | 无接缝 | 不发起模型请求，未计数 |
| 代理启动次数 | 仅 `workflow-script` 后端（`task.maxAgentCalls`，1–32，每次 `agent()` 启动前同步检查） | V0.1 已验证 |
| 模型请求次数 | 宿主 `agent/request` 瀑布（拦截器） | 逻辑已实现并夹具验证；**真实宿主未验证** |
| 重试次数 | 同上（重试会重新进入瀑布，因此各自预占一次） | 语义由随包代码只读确认 |
| token 用量 | 无 | 只能在运行后按会话日志复算 |

| 后端 | 能否硬限制"启动多少次模型调用" | 依据 |
| --- | --- | --- |
| `workflow-script`（three-agent-mvp） | 能，`maxAgentCalls`，每次 `agent()` 启动前同步检查 | V0.1 已验证 |
| `agent-teams`（候选） | **不能**（代理启动层面） | 插件内无调用计数器；`members.ts:900/945` 通过 `ctx.subagents` 起子代理，followup / 自动修复 / resume / fallback 都会各自发起新请求 |
| 宿主 `agent/request` 拦截器（新增） | 能拦**模型请求**，不能拦**代理启动** | `dsh-agent-loop/lib/index.js:1170-1195`：瀑布在 `llm.prepareCall()` 之前，抛错即不发请求；重试 `continue` 回到 `while` 顶部（`:1134` → `:1050`） |

因此：用 agent-teams 时，计划必须带 `CALL_CAP_PARTIAL` 警告并写明真实原因，不得沿用"8 次硬限制"的承诺。计划里 `callAccounting.hardCapApplicable` 与 `synchronousLimit` 必须如实填写，`readiness.budgetProtection` 只能是 `"allocation-plan-only"`，并把 `CALL_CAP_NOT_ENFORCEABLE` 记进 `missingForExecution`——**这条缺口与"执行适配还没写"是两件独立的事，不能被后者掩盖**。

`maxMembers`（插件上限 8 个成员）只是成员数量限制，**不能**当作模型调用次数上限使用；提示词里写"最多调用 N 次"也不是拦截。

## 5. 使用方式（只读、离线）

```bash
# 出计划（0 = ready，2 = blocked，1 = 输入错误）
node orchestration/cli.mjs plan \
  --config orchestration/examples/plan-agent-teams.json \
  --pricing orchestration/data/pricing-snapshot.portkey-72e1084.json \
  --host-catalog orchestration/data/host-catalog.dsh-0.2.0-rc.2.json \
  --now 2026-10-17T18:00:00Z

# 翻译成 agent_teams_create 的入参形状（只生成 JSON，不调用工具）
node orchestration/cli.mjs translate --config ... --pricing ...

# 规范化落盘 + 回读比对（证明配置可恢复，不证明会话可恢复）
node orchestration/cli.mjs save --config ... --dir <临时目录>
```

当前 demo 的输出（`--now 2026-10-17T18:00:00Z`，带 `--host-catalog`）：3 个成员，估算 `USD 0.024418` / `0.0236544` / 未知，预算 `USD 25`（10 / 10 / 5）；blocker 为 `BACKEND_NOT_INSTALLED`、`ESTIMATES_INCOMPLETE`、`HOST_CATALOG_MODEL_UNLISTED`；警告含 `CALL_CAP_PARTIAL`、`PRICE_CHANNEL_UNSPECIFIED`、`HOST_CATALOG_PRICE_CHANNEL_DIFFERS`、`ESTIMATE_PARTIAL`；退出码 2。

demo 暴露的真实问题（不是夹具缺陷）：portkey 快照里 `deepseek-v4-flash` 不在宿主目录中，`deepseek-v4-pro` 虽然两边都有，但快照价（43.5/87 美分/百万）与宿主目录价（132/396 美分/百万）差约 3 倍——所以**不能用旧价格快照决定运行模型或预算**，必须按宿主目录的实际渠道价重算。

```js
// 执行适配将来必须提供的形状（当前只有探测与翻译）
executePlan(plan, { backend, evidenceDir }) -> {
  status: 'unavailable',                       // 现在恒为 unavailable

createAgentRequestListener({ modelRequests }) -> {
  event: 'agent/request',
  scope: null,                    // 未打标签 = 全局可见

```

将来真正接入时需要新增、且必须逐个验证的东西：`create` → `approve` → 派工 → 收尾的状态机；拦截器在真实宿主里的安装形态与生命周期；证据目录与插件状态的对接（不得直接改写插件内部状态文件）；中断/恢复语义（中止发生在预占之后会**多计**一次，不会少计）。

## 7. 本阶段不声称的能力

- 不声称"多模型协作已跑通"：本轮没有任何真实模型调用。
- 不声称"预算是硬上限"：它只是计划分配。
- 不声称"agent-teams 已接入"：只有探测与翻译，执行恒为 `unavailable`。
- 不声称"启动前计数已验证"：拦截器只在夹具里验证过，真实宿主未安装。
- 不声称"手机审批可用"：只有审查与准备清单。
- 不声称"价格是实时的"：快照是某 commit 的离线拷贝，新鲜度未知；与宿主目录价的对照见 §2.3。
- 持久化夹具只证明**配置文件**可规范化恢复，不证明真实 Agent 会话的冷恢复。
