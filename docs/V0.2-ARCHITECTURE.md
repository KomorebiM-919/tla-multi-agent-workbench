# V0.2 最小架构：配置 / 计划 / 执行适配三层

本文描述 V0.2「多模型手动分工 + 预算规划」的最小架构、数据契约与**能力边界**。它描述的是**已实现的离线原型**，不包含真实模型调用。

## 1. 分层

```
┌───────────────────────────────────────────────────────────────┐
│ TLA 自有层（本阶段已实现，全部离线）                          │
│  配置校验  →  价格查询  →  费用估算  →  预算分配  →  计划     │
│  orchestration/config.mjs   pricing.mjs   estimate.mjs        │
│  orchestration/money.mjs    plan.mjs    cli.mjs               │
└───────────────────────────┬───────────────────────────────────┘
                            │ 计划（tla.v02-plan/v1）
┌───────────────────────────▼───────────────────────────────────┐
│ 执行适配层（orchestration/adapters/agent-teams.mjs）          │
│  兼容性探测 → 计划翻译 → 执行（未实现，恒返回 unavailable）   │
└──────┬──────────────────────────────────┬─────────────────────┘
       │                                  │
┌──────▼───────────────┐        ┌─────────▼────────────────────┐
│ workflow-script 后端 │        │ agent-teams 后端（候选）      │
│ 已验证：three-agent- │        │ 未安装、未执行；每次 spawn 才 │
│ mvp；同步调用次数硬顶│        │ 解析一次调用配置，无全局硬上限│
└──────────────────────┘        └──────────────────────────────┘

旁路（不进入执行链）：
  价格快照（离线 JSON，来自 portkey-models@72e1084）
  用量报告（TLA 已有 usage 证据目录，本轮未改动）
  手机通道（独立通道，见 docs/V0.2-MOBILE-CHANNEL.md）
```

三条设计原则：

1. **执行后端可替换，验收/证据/审批/预算门禁留在 TLA。** 换后端不能改变"谁批准、证据在哪、预算谁算"。
2. **不确定就阻断。** 价格未知、币种不符、快照过期、后端不可用、调用上限无法保证——一律变成计划里的 blocker 或 warning，绝不默认成 0 或"应该没问题"。
3. **计划不是运行。** 本阶段所有产物都是计划与翻译结果，`executePlan()` 恒返回 `unavailable`。

## 2. 三个数据契约

### 2.1 运行配置 `tla.v02-run-config/v1`

```json
{
  "schema": "tla.v02-run-config/v1",
  "runId": "v0.2-plan-demo-20261018T000000Z",
  "roles": {
    "lead":   { "provider": "deepseek-official", "model": "deepseek-v4-pro", "reasoningEffort": "high" },
    "worker": { "provider": "deepseek-official", "model": "deepseek-v4-flash" },
    "reviewer": { "provider": "moonshot", "model": "moonshot-v1-8k" }
  },
  "ownerRole": "lead",
  "router": { "enabled": false, "policy": "none" },
  "budget": {
    "currency": "USD",
    "totalMinor": 2500,
    "allocations": [
      { "role": "lead", "basisPoints": 4000 },
      { "role": "worker", "basisPoints": 4000 },
      { "role": "reviewer", "basisPoints": 2000 }
    ]
  },
  "pricing": {
    "snapshotPath": "orchestration/data/pricing-snapshot.portkey-72e1084.json",
    "maxAgeHours": 168,
    "providerAliases": { "deepseek-official": "deepseek" }
  },
  "estimates": {
    "perCall": { "inputTokens": 20000, "outputTokens": 4000, "cacheReadTokens": 8000 },
    "calls": { "lead": 2, "worker": 6, "reviewer": 2 }
  },
  "backend": { "kind": "workflow-script", "workflow": "three-agent-mvp", "task": { "...": "..." } }
}
```

校验规则（全部实现并测试）：

- `router.enabled` 必须为 `false`、`policy` 必须为 `none`；其它写法直接 `ROUTER_UNSUPPORTED`。
- 每个角色必须显式写 `provider` 与 `model`（缺一个即 `ROUTE_INCOMPLETE`）。
- 角色的 `selection` 只能是 `manual`；写 `auto` 等即 `SELECTION_UNSUPPORTED`。
- 角色出现 `fallback` 即 `FALLBACK_UNSUPPORTED`（本阶段不允许自动降级）。
- `ownerRole` 必须存在于 `roles` 中。
- `budget.allocations` 必须覆盖每个角色，且基点之和**恰好** 10000。
- `pricing.providerAliases` 必须是非空字符串映射，且禁止自映射。
- 币种只支持 1 主单位 = 100 最小单位的币种（USD/CNY/EUR）；JPY 之类直接拒绝，而不是悄悄按两位小数处理。

### 2.2 价格快照 `tla.pricing-snapshot/v1`

每条价格带 `provider`/`model`/`mode`/`prices{input,output,cacheRead,cacheWrite}/provenance/unknownFields`，整份快照带 `snapshotId`、`currency`、`capturedAt`、`source{repository,commit,license,files}`。金额单位是**微-分/百万 token**（整数），不存在浮点价格。

单价缺失不会被补 0，而是写进该条的 `unknownFields`：`cacheReadPricing`、`cacheWritePricing`、`offPeakPricing`。其中 `offPeakPricing` 是**所有**条目都带——portkey 数据里根本没有峰谷字段（见复用决策文档 §3），所以本阶段的估价一律不含峰谷折扣。

### 2.3 计划 `tla.v02-plan/v1`

成员行是"这次谁用哪个模型、大概花多少、分到多少"的唯一事实来源：

| 字段 | 含义 |
| --- | --- |
| `provider` / `model` | 执行的模型（与配置完全一致，不做覆盖） |
| `selection` / `selectionSource` | 固定为 `manual` / `config (manual)` |
| `isOwner` | 是否负责人角色 |
| `priceStatus` / `priceProvenance` / `priceLookup` | 价格是否已知、来自哪、实际用哪个 provider 查的（含 `aliased`） |
| `calls` / `estimatedMicroMinor` | 调用次数假设与估算（未知时为 `null`，不是 0） |
| `allocationMicroMinor` / `withinAllocation` | 分配额与是否超分配 |
| `unknownFields` | 该成员自身未确定的项（如 `cacheRead`、`cacheWrite`、`offPeakPricing`） |

顶层还包含 `totals`、`routerGuard{mode:"manual-pinned",autoRoutingEnabled:false,overridable:false}`、`backend`、`callAccounting`、`budgetEnforcement`、`status`、`blockers[]`、`warnings[]`、`limitations[]`、`notProofOf[]`。

**就绪状态拆成五个维度**，任何一项缺失都不得 `status: "ready"`：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| `readiness.configValid` | `true` | 计划只由校验通过的配置生成 |
| `readiness.estimatesAvailable` | `true`/`false` | 所有角色都有已知价格且能估算 |
| `readiness.backendCompatible` | `true`/`false` | 宿主/插件版本/公开导出/注入服务都对得上 |
| `readiness.executionImplemented` | `true`/`false` | TLA 侧真的实现了执行适配（当前只有 `workflow-script` 为真） |
| `readiness.budgetProtection` | `"call-count-hard-cap"` / `"allocation-plan-only"` | 是否有"每次模型启动前"的同步计数闸门 |

`missingForExecution[]` 列出还缺什么（`ESTIMATES_INCOMPLETE`、`BACKEND_UNAVAILABLE`、`BACKEND_EXECUTION_NOT_IMPLEMENTED`、`CALL_CAP_NOT_ENFORCEABLE`），`executable` 当且仅当它为空**且** `blockers` 为空；`status` 由 `executable` 推导。**"插件装了、兼容探测通过"不等于可执行**——这条是复审时发现并修掉的真实缺陷（旧实现会把兼容探测结果直接当成 ready）。

## 3. 金额语义（务必区分）

- 预算是**计划上限**，不是付款、不是供应商余额、不是跨平台资金划拨。计划里固定写 `budgetEnforcement: "allocation-plan-only"`。
- 分配用**基点**（整数，总和 10000）+ **最大余数法**，保证各角色分额之和**恰好**等于总额，不需要浮点容差。余数相同时按**声明顺序**补给前面的角色（确定性，换顺序会换到另一角色，但守恒不变）。
- 估算用整数微单位；调用次数与 token 数都是**人工假设**（`config.estimates`），不是历史实测。
- `tokens × 单价 / 100 万` 一律**向上取整**（`divCeil`）：估算是上界，任何非零用量都不会被算成 0，也不会低于按价目计算的理论值。旧实现用 half-up，`costForTokens(1, 1)` 会得到 0。
- 除法中间量在 2^53 附近会静默舍入：`divCeil` 先判断 `numerator > MAX_SAFE_INTEGER - (denominator - 1)` 再相加，`divRoundHalfUp` 对 `2 × magnitude + denominator` 做安全整数检查，越界一律 `MONEY_OVERFLOW`，不返回"看起来对"的错值。
- 缓存读价缺失时按**输入价**计为上界并标注 `conservative`；缓存写价缺失同样按输入价计上界。都不按 0 计——那样会把"未知"伪装成"便宜"。
- 没有汇率换算：币种不一致直接阻断，不做跨币种折算。金额刻度目前假设 `1 主单位 = 100 最小单位`，只支持 `USD`/`CNY`/`EUR`，其他币种直接拒绝（`BUDGET_CURRENCY_INVALID` / `PRICING_INVALID`）。

## 4. 调用计数边界（这是本阶段最重要的限制）

| 后端 | 能否硬限制"启动多少次模型调用" | 依据 |
| --- | --- | --- |
| `workflow-script`（three-agent-mvp） | 能，`maxAgentCalls` 1–32，每次 `agent()` 启动前同步检查 | V0.1 已验证 |
| `agent-teams`（候选） | **不能** | 插件内无调用计数器；followup / 自动修复 / resume / fallback 都会各自发起新请求，编排层没有同步闸门 |

因此：用 agent-teams 时，计划必须带 `CALL_CAP_PARTIAL` 警告并写明真实原因，不得沿用"8 次硬限制"的承诺。计划里 `callAccounting.hardCapApplicable` 与 `synchronousLimit` 必须如实填写，`readiness.budgetProtection` 只能是 `"allocation-plan-only"`，并把 `CALL_CAP_NOT_ENFORCEABLE` 记进 `missingForExecution`——**这条缺口与"执行适配还没写"是两件独立的事，不能被后者掩盖**。

`maxMembers`（插件上限 8 个成员）只是成员数量限制，**不能**当作模型调用次数上限使用；提示词里写"最多调用 N 次"也不是拦截。

## 5. 使用方式（只读、离线）

```bash
# 出计划（0 = ready，2 = blocked，1 = 输入错误）
node orchestration/cli.mjs plan \
  --config orchestration/examples/plan-agent-teams.json \
  --pricing orchestration/data/pricing-snapshot.portkey-72e1084.json \
  --now 2026-10-17T18:00:00Z

# 翻译成 agent_teams_create 的入参形状（只生成 JSON，不调用工具）
node orchestration/cli.mjs translate --config ... --pricing ...

# 规范化落盘 + 回读比对（证明配置可恢复，不证明会话可恢复）
node orchestration/cli.mjs save --config ... --dir <临时目录>
```

当前 demo 的输出（`--now 2026-10-17T18:00:00Z`）：3 个成员，估算 `USD 0.024418` / `0.0236544` / `0.0272`，合计 `USD 0.0752724`，预算 `USD 25`（10 / 10 / 5），唯一 blocker 是 `BACKEND_NOT_INSTALLED`，另有 `CALL_CAP_PARTIAL` 与缓存价上界两条警告；退出码 2。注意 demo 用的是"插件未安装"的探测事实，所以 blocker 是 `BACKEND_NOT_INSTALLED`；若探测为"已安装且兼容"，blocker 会换成 `BACKEND_EXECUTION_NOT_IMPLEMENTED`，`status` 仍然是 `blocked`。

## 6. 未实现的类型契约（不含 mock）

```js
// 执行适配将来必须提供的形状（当前只有探测与翻译）
executePlan(plan, { backend, evidenceDir }) -> {
  status: 'unavailable',                       // 现在恒为 unavailable
  code: 'BACKEND_EXECUTION_NOT_IMPLEMENTED',   // 不允许用 mock 通过冒充
  executedModelCalls: 0
}
```

将来真正接入时需要新增、且必须逐个验证的东西：`create` → `approve` → 派工 → 收尾的状态机；每次模型启动前的计数闸门（若插件不提供，就要如实降级为"无法硬限制"）；证据目录与插件状态的对接（不得直接改写插件内部状态文件）；中断/恢复语义。

## 7. 本阶段不声称的能力

- 不声称"多模型协作已跑通"：本轮没有任何真实模型调用。
- 不声称"预算是硬上限"：它只是计划分配。
- 不声称"agent-teams 已接入"：只有探测与翻译，执行恒为 `unavailable`。
- 不声称"手机审批可用"：只有审查与准备清单。
- 不声称"价格是实时的"：快照是某 commit 的离线拷贝，新鲜度未知。
- 持久化夹具只证明**配置文件**可规范化恢复，不证明真实 Agent 会话的冷恢复。
