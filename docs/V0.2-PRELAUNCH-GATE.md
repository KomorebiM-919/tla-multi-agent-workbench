# V0.2 启动闸门：预算保护不能依赖"插件已经装好"

状态：本地实验实现并验证。**未接入任何真实模型端点，不构成宿主级强制保护**。日期：2026-10-18。

## 1. 要修的问题

阶段 1/2 的事故记录表明：预算拦截逻辑放在 DSH 插件里不可靠。

- 插件 `apply()` 抛错时，宿主只打印 `dsh: warning: 1 entry did not activate` 并**继续运行**；实测随后在无预算状态下发出 2567 次模型请求，直到手工杀进程。
- 因此"插件已安装/配置里存在该条目"不能证明"保护生效"；"某个状态变量说 mounted"同样不能。

结论：判定"能不能发请求"的位置必须独立于被保护的插件，并且**默认拒绝**。

## 2. 设计：三层职责分离

1. **预算闸门（gate）**：进程内的本地 HTTP 代理，只绑 `127.0.0.1`，只有一个上游（也必须是回环）。默认拒绝，只有在"持有有效租约 + 额度未用尽"时才建立上游连接并放行。额度用尽/租约过期/已撤销/正在关闭 → 返回 403 `TLA_GATE_DENIED`，**不建上游连接**。
2. **插件（attestation only）**：`tla-prelaunch-budget` 不再承担强制。它只做两件事：挂载时写 `mounted` 心跳、每次预占写 `reserved`/`rejected`。它缺不缺失都不影响闸门的默认拒绝。
3. **启动器（preflight + lease）**：`tools/gated-run.mjs` 在启动宿主前校验**生效配置**里的 provider `baseURL` 指向闸门，并逐个 provider 实例校验覆盖率（见 §5）；不满足就退出码 3 且不启动宿主。随后启动宿主，读到新鲜 `mounted` 心跳才发租约，并按 `ttl/3` 续期；心跳过期 → 撤销租约并 SIGTERM。

闸门自己也能读心跳文件（`mountProof`）：宿主启动后立刻发首个请求时，插件挂载事件通常已经落盘，闸门在无租约时同步检查这份新鲜证明，命中才当场授权，同一事件只消费一次，撤销后不再重新授权。这样消除了"先等心跳再发租约"与"首个请求立刻到达"之间的竞态。

## 3. 实现文件

- `orchestration/gate/gate.mjs`：`createBudgetGate({ upstream, modelRequests, leaseTtlMs, logPath, mountProof })`。控制面**只有只读状态查询**（`GET /__tla/gate/status`，仅回环）；`/__tla/gate/{lease,heartbeat,revoke}` 一律 405 `GATE_CONTROL_READ_ONLY`——租约的发放/续期/撤销只允许**同进程函数调用**（`grantLease/heartbeat/revoke/close`），本机其他进程无法通过 HTTP 改变闸门状态。租约是显式状态机：`none/active/expired/revoked`；`grantLease` 在关闭或永久撤销后抛错且**不复位**已消耗计数；过期租约的迟到心跳不复活；已撤销租约不能续期；事件日志 `listening/lease-granted/lease-from-mount/heartbeat/heartbeat-rejected/lease-revoked/allowed/denied/upstream-error/closed`。
- `orchestration/gate/preflight.mjs`：**受限 YAML 子集的结构化解析**（`parseDumpConfigStrict`，2 空格缩进、块式序列/映射、`!!js` 标签值按不可信处理、空 `[]`/`{}` 可接受；制表符、非空流式集合、锚点/别名、多文档、重复键/重复 id 一律拒绝）＋ `checkBaseUrl`（按路径段比较，避免端口前缀误匹配）＋ **运行生命周期状态机** `walkRunLifecycle`（首条必须是 `mounted`；只接受 `mounted/heartbeat/reserved/rejected/unmounted`；坏行 `PROOF_UNREADABLE`、时间倒序 `PROOF_TIME_ORDER`、重复 `mounted` `PROOF_DUPLICATE_MOUNT`、`unmounted` 之后任何事件 `PROOF_AFTER_UNMOUNT`、未来时间 `PROOF_FUTURE`、早于宿主启动 `PROOF_PRE_START`、结束时 `RUN_ENDED`）＋ `evaluateMountProof`（**只判身份/终态，不再用 `mounted` 年龄杀健康长跑**）＋ `checkProtectionHeartbeat`（**只看最新一次 `heartbeat` 的年龄**）＋ `decideStart`（覆盖率必须可验证、无未受保护实例、至少一个受保护 provider）＋ `extractProviderCoverage`（逐个 provider 实例判定是否指向闸门；未识别适配器记 `unknown` 并拒绝启动；自带模型端点的随包组件按端点是否指向闸门判定）。
- `tools/gated-run.mjs`：启动器；退出码 `0` 正常、`1` 宿主失败、`2` 参数/内部错误、`3` 保护未建立（宿主已终止）、`4` 运行中保护丢失。
- `tests/v02-gate.test.mjs`：15 场景 / 150 断言（含控制面只读、租约状态机、运行级挂载证明、生命周期（长跑/卸载终态/重复挂载/时间倒序/损坏日志）、闸门级上游计数、并发、YAML 严格性、覆盖率（含自带模型端点的随包组件）、探测失败分类、终止升级）。
- `tests/v02-prelaunch-budget.test.mjs`：10 场景 / 46 断言（含插件真实接线的 `mount/heartbeat/reserved/unmounted` 事件、`runId` 缺失拒绝挂载、状态损坏/丢失/重启三种 fail-closed、`apply` 在 IO 失败时**会**抛错）。

### 4.1 独立审查后的加固（同日第二轮）

外部静态审查（P0/P1 清单）后有针对性重写，全部为本地修复与离线/隔离验证：

| 项 | 问题 | 现在的行为 |
| --- | --- | --- |
| P0-1 | 控制面以"仅回环"当认证 | 写接口全部删除（405 `GATE_CONTROL_READ_ONLY`）；租约只由同进程调用 |

### 4.2 独立复审后的生命周期修复（同日第三轮，状态：待独立复核）

复审用两个可复现反例指出生命周期判定仍然"只看首尾"：

1. **健康长跑被误停**：`mounted` 发生在 `now-20000ms`、`heartbeat` 发生在 `now-10ms`、`maxAgeMs=8000` 时，`checkProtectionHeartbeat` 先调 `evaluateMountProof`，用**最初 `mounted` 的年龄**判 `PROOF_STALE`，于是运行还没掉保护就被判"心跳过旧"。
2. **卸载后迟到心跳被接受**：`mounted(now-1000) → unmounted(now-500) → heartbeat(now-10)` 时 `evaluateMountProof` 返回 `ok:true`——它只看首条 `mounted` 和最后一条事件，`unmounted` 不是终态。

修复前反例输出保存在 `tests/.scratch/v02-review/prefix-counterexamples-before.txt`（长跑 `PROOF_STALE` / `HEARTBEAT_STALE`；卸载后心跳 `ok:true`；重复 `mounted` `ok:true`），修复后同一脚本输出 `prefix-counterexamples-after.txt`（长跑 `ok:true` + `ageMs:10`；卸载后 `PROOF_AFTER_UNMOUNT`；重复挂载 `PROOF_DUPLICATE_MOUNT`）。

修法：

- 新增 `walkRunLifecycle`：按**完整事件序列**判定身份与终态（首条必须 `mounted`；`unmounted` 之后任何事件都是 `PROOF_AFTER_UNMOUNT`；重复 `mounted` 是 `PROOF_DUPLICATE_MOUNT`；时间倒序是 `PROOF_TIME_ORDER`；坏行是 `PROOF_UNREADABLE`）。`unmounted` 对本次运行是**终态**；重新挂载必须换新的运行身份，不能隐式复活。
- `evaluateMountProof` 不再接收 `maxAgeMs`：它只回答"这次运行的挂载身份是否成立、是否已结束"。
- `checkProtectionHeartbeat` 改为看**最新一次 `heartbeat`** 的年龄，因此健康运行可以跨任意多个心跳窗口继续存活；停止心跳后仍会在 `maxAgeMs` 内被撤销。
- `runEndedByLastEvent` 的语义改为"只要出现过 `unmounted` 就是终态"，读不出/损坏时返回 `true`（fail-closed，闸门直接永久撤销）。

覆盖面变化：

- `tests/v02-gate.test.mjs` 升到 **15 场景 / 150 断言**。新增场景 `scenarioLifecycleAtGate` 用**上游请求计数**区分"判定函数误接受"与"闸门真的转发"：长跑放行且上游恰好 1；卸载后迟到心跳 403 且上游仍为 1；重复 `mounted` 403 且上游仍为 1。
- 覆盖率语义补强：白名单只能证明"组件在默认 profile 里存在"，不能证明"它不调用模型"。宿主源码里有两个随包组件自带模型端点——`@deepseek-ai/dsh-web-search-deepseek` 默认 `baseURL` 为 `https://api.deepseek.com/anthropic/v1` 并 POST `${baseURL}/messages`，`@deepseek-ai/dsh-deepseek-account-platform` 默认 `inferenceOrigin` 为 `https://api.deepseek.com`（本机代理再转发）。它们现在按**端点是否指向闸门**判定（`MODEL_ENDPOINT_COMPONENTS`），默认端点即 `unguarded`、阻止启动；指向闸门或被禁用才放过。
- "名字带 llm 但不是 provider 适配器"的组件为什么仍受约束：`@deepseek-ai/dsh-session-title-first-prompt-llm` 注入 `sessionTitle/llm/sessions`、不自己连网；`@deepseek-ai/dsh-session-title-llm` 在 `lib/index.js:226` 调 `ctx.llm.stream(options)`；`@deepseek-ai/dsh-agent-loop` 在 `lib/index.js:1189` 调 `llm.prepareCall(...)`、`:1072` 调 `llm.stream(...)`。这些消费方共享宿主的 `llm` 服务，真正的 HTTP 只发生在 provider 适配器里，因此同一道闸门对它们有效；实验 overlay 里另外显式禁用了 `session-title` 与 `session-title-llm`。

真机长跑复验（`tests/.scratch/v02-stage2/round3/long/`，假模型服务 `127.0.0.1:18795`、闸门 `18794`、心跳间隔 300 ms、`--heartbeat-max-age-ms 2000`）：

| 指标 | 值 |
| --- | --- |
| 运行时长（`mounted` → `unmounted`） | 6.61 s = **3.3 个心跳窗口** |
| 插件 `reserved` | 6 |
| 闸门 `allowed` | 6 |
| 上游 `accepted` | 6（`deepseek-flash`，`tool_use`×5 + `end_turn`） |
| 拒绝 | 0 |
| 结束 | `EXIT=0`、`result=host-ok` |

这证明"超过两个心跳有效期仍正常放行、且计数一致"不是短任务偶然通过。

## 5. 实际网络路径与绕过分析

模型请求由 deepseek 适配器发出：`POST <baseURL>/v1/messages`（`dsh-llm-deepseek` 的 `messagesApiRoot`；实测宿主走 `/v1/messages`）。`baseURL` 来自每个 provider 实例的配置，而生效配置里**不止一个实例**：

| 实例 id | 包 | 路由 provider | 默认 baseURL |
| --- | --- | --- | --- |
| `llm-deepseek` | `@deepseek-ai/dsh-llm-deepseek-api-key` | `deepseek-official` | `https://api.deepseek.com/anthropic` |
| `llm-deepseek-account` | `@deepseek-ai/dsh-llm-deepseek-account` | `deepseek-account` | 同 DeepSeek 消息端点（无独立 baseURL 配置项时跟随默认） |
| `llm-pi-ai` | `@deepseek-ai/dsh-llm-pi-ai` | 由 `providers:` 决定 | 未配置 `providers:` 时不注册任何路由 |

**闸门不是网络层拦截**：它没有进宿源码、不装防火墙，只在 `baseURL` 被覆写到闸门时位于路径上。

- **run G（绕过确实存在）**：把同一个 `llm-deepseek` 的 `baseURL` 指向另一个回环端点 `127.0.0.1:18779`，不经启动器直接运行宿主 → 请求**直接到达该端点**（`accepted:true`、`model: deepseek-flash`、`stopReason: end_turn`），宿主正常返回脚本答案，闸门完全看不到这条请求。
- **run F(strict)（防线可执行）**：生效配置里 `llm-deepseek-account.baseURL` 指向 18779 时，`extractProviderCoverage` 把它判为 `unguarded`，启动器以 `PROVIDER_NOT_GATED` 拒绝启动，宿主未启动，18779 收到 0 条请求。
- **重试**：宿主每次尝试都会重新触发 `agent/request`（`dsh-agent-loop/lib/index.js:1179`，重试路径 `:1134 → :1050`），而 provider 配置不变，所以重试仍走闸门，但每次尝试各占一次额度。
- **fallback**：`deepseek-official` 与 `deepseek-account` 是两条独立路由，各自解析凭据、互不 fallback（`dsh-llm-deepseek/README.md:88`）。两条都指向闸门才谈得上覆盖（run E 即如此）。
- **resume**：复用同一 provider 配置，代码层面未见单独端点；**未做真实 resume 实验**，列为未验证。

已受保护 / 未受保护：

- 已保护（真实宿主已验证）：队长请求、成员请求（同一 provider 配置，run3/run4 已证明成员走同一路由）、工具调用之后的后续请求（run E 第 2 次请求即此类）、重试（每次尝试都过闸门）。
- 未受保护：任何未指向闸门的 provider 实例（默认配置里的 `deepseek-account`；配置了 `providers:` 的 `llm-pi-ai`）；宿主进程之外的其它程序；未来版本可能新增的硬编码端点。
- **已转发 vs 未转发**：闸门的 `used`/`allowed` 只统计**已转发**请求；403 表示**没有建立上游连接**。已转发的请求可能已经在供应商侧产生费用，闸门无法撤回，本实验也不承诺这一点。

## 7. 限制与未证明项

- **闸门只在"模型请求确实经由被覆写的 `baseURL`"时有效**；run G 已证明换个端点就绕过。因此保护强度等于"覆盖率校验的完整性"，而不是"闸门存在"。
- 覆盖率校验的对象是**生效配置里的每一个组件条目**。`@deepseek-ai/dsh-llm-*` 之外的组件按"受信任组件白名单"判定（`orchestration/gate/known-components.mjs`，取自隔离 profile 在空配置下的 `dsh --dump-config` 清单）：白名单内的视为与模型请求无关，**白名单外的一律记为 unknown 并拒绝启动**；缺 `name` 的条目同样记 unknown。因此"名字不带 `llm` 但自己会发请求"的插件（例如 `@acme/router`）不会被静默漏掉，代价是新增宿主组件时必须重新登记白名单。
- 覆盖率校验读的是宿主自己回答的生效配置（`--dump-config` 打印 YAML 且退出码可能为 `-1`，判据只能是"有没有输出"），不是本工具推演出来的配置。被检查的配置与真正启动的实例由**同一组参数**派生（见 §7.1），但"宿主如实回答自己的配置"仍是本实验无法自证的信任前提。
- 沙箱下 `spawnSync(..., { encoding })` 与默认 `spawn` 管道都会 `EPERM`；启动器因此把 stdout/stderr 直接接到文件描述符再读文件（stdout 与 stderr 分开落盘，配置只取 stdout）。`--dump-config-from` 已删除。
- 心跳只证明"插件写入了 `mounted`"，不证明监听器仍在工作；运行中失效靠租约过期 + `revoke`（夹具已测），真实宿主只测到"心跳过旧即拒绝"。
- **未验证**：真实 `resume`/`fallback`/自动返工路径；跨进程/跨会话的预算共享；取消请求是否被供应商实际计费；宿主对"插件激活失败"的行为是否会在其他版本变化；并发在真实宿主里是否与夹具同样原子（夹具是单进程同步预占）。
- 闸门是**本地实验工具，不是宿主级强制保护**：它没有进入 DSH 源码，也没有被宿主默认启用。
- 进入受监督真实实验的前提不是"闸门能跑"，而是：**生效配置里所有 provider 实例都指向闸门**。这条判定现在由启动器强制（§7.1），命令行上没有任何放宽开关。

## 7.1 生效配置与启动实例的可信绑定

旧实现在沙箱里读不到管道输出，于是允许调用方先手工跑一次 `--dump-config` 落成文件、再用 `--dump-config-from` 交给启动器。这条路径的问题是**被检查的配置可以不是被启动实例的配置**——它只是调用方的说法。

现在的做法：

1. **由启动器自己取配置**：用 `buildInvocation()` 派生 `--expose-internals <cli> --profile <p> [--patch <f>...] --dump-config`，把 stdout 写到 `run-dir/effective-config.yml`（stderr 单独一份），再读这段字节。`--dump-config-from` 已删除，出现即按用法错误退出（exit 2）。
2. **同源派生**：真正启动宿主时用同一个 `buildInvocation()`，只把叶子参数从 `--dump-config` 换成 prompt；可执行文件、`cli.js`、profile、patch 列表、工作目录（`run-dir`）、环境变量（`ELECTRON_RUN_AS_NODE`、`DSH_HOME` 等）完全一致。summary 写入 `config.binding`（来源、profile、patch 文件名、`cwdIsRunDir`、环境键名、dump 摘要）与 `invocation`（`sameCommandAsProbe`/`sameProfileAsProbe`/`samePatchesAsProbe`/`cwdIsRunDir`）。
3. **拒绝启动的条件**（全部 exit 3，此时宿主进程根本没被创建）：
   - `CONFIG_UNREADABLE`：取不到配置（stdout 为空、进程起不来、profile 不存在）；
   - `CONFIG_COVERAGE_UNKNOWN`：配置读到了但解析不出 provider 覆盖率；
   - `NO_GATED_PROVIDER`：没有任何 provider 实例指向闸门；
   - `PROVIDER_NOT_GATED`：存在未指向闸门的 provider 实例（detail 列名字）；
   - `BASE_URL_MISMATCH`：主 provider 的 `baseURL` 不是闸门地址（**只在确实读到配置时**才报，避免把"缺输入"说成"地址错"）；
   - `GATE_NOT_READY`：闸门自身状态不可读。
4. **没有放宽开关**：`--allow-ungated-providers` 已删除，出现即按用法错误退出。run F/override 那次演示是在该开关还存在时做的，现在无法复现这条路径——这正是本轮的目的。

真实宿主验证（隔离 profile `stage1`，假模型服务只绑 `127.0.0.1:18777`，闸门 `127.0.0.1:18778`）：

| 运行 | 配置 | 结果 | 宿主 | 上游请求 |
| --- | --- | --- | --- | --- |
| run I | 启动器自取，两个 provider 都指向闸门 | exit 0、`host-ok`、`guarded=[llm-deepseek, llm-deepseek-account]`、`notConfigured=[llm-pi-ai]`、闸门 `used=1` | 启动并完成 | 1（就是放行的那次） |
| run J | overlay 只改 `llm-deepseek`，`llm-deepseek-account` 保持默认端点 | exit 3、`refused-before-host-start`、blocker `PROVIDER_NOT_GATED`、`config.sha256=d8e103ab…` | **未启动** | 0（前后都是 2 条，无新增） |
| run K | profile 不存在 → `--dump-config` 无输出 | exit 3、`CONFIG_UNREADABLE`（不再附带 `BASE_URL_MISMATCH`）、`config.sha256=null` | **未启动** | 0 |

## 7.2 配置探测与挂载证明的隔离

审查发现的问题：探测（`--dump-config`）与正式宿主原先共用同一个 `TLA_RUN_ID`。于是只要探测阶段写下了本次 runId 的 `mounted`，即使正式宿主的插件根本没挂上，闸门也会把这条证明当成"本次运行已挂载"并发出租约——保护被"探测阶段的副产品"冒充。

实测与修法：

1. **真实 DSH 的 `--dump-config` 不激活插件**。在隔离 profile 里装着拦截器、overlay 里 `insert` 了 `tla-prelaunch-budget`（`stateFile`/`eventLog` 指向空目录）、`TLA_RUN_ID=probe-check-runid-1` 的条件下执行 `dsh --profile stage1 --patch … --dump-config`：dump **里确实有** `- id: tla-prelaunch-budget` 条目，但 `events.jsonl` 与 `budget-state.json` **都没有被创建**（`Test-Path` 为 false）。dump 里的 `disabled: !!js '…'`、`desktopPlatform: !!js >-` 保持 JS 标签的未求值形态，也说明这一步只做配置合成、不实例化插件。所以"探测泄漏 mounted"不是真实宿主的正常行为，而是必须有测试拦住的假设。
2. **身份分离**：探测改用 `<runId>-probe`（`probeRunIdOf()`），只有正式宿主拿到 `TLA_RUN_ID=<runId>`。环境摘要比对时排除 `TLA_RUN_ID`，其余环境键仍必须一致；summary 记录 `runIdSeparatedFromProbe` 及两边的 runId。
3. **证明的三道闸**（`evaluateMountProof`）：`PROOF_FOREIGN_RUN`（事件 runId 不匹配，`-probe` 的证明因此无效）、`PROOF_PRE_START`（`mounted` 早于宿主启动 `notBefore`，容忍 2 秒时钟偏差）、`PROOF_NO_HEARTBEAT`（只有 `mounted`、没有任何 `heartbeat` 就授权）。闸门装载 `mountProof` 时固定 `requireHeartbeat: true`。
4. **负向复现**：离线脚本先写一条同 runId 的 `mounted` 再建闸门发请求，修复前拿到租约（`lease.state === 'active'`、日志出现 `lease-from-mount`）；修复后这条证明分别因 `PROOF_FOREIGN_RUN`/`PROOF_PRE_START`/`PROOF_NO_HEARTBEAT` 被拒。夹具另有端到端用例（stub 只写 `<runId>-probe` 的 mounted+heartbeat）→ `EXIT=3`、`host-exited-before-protection`、上游 0 新增。

测试计数因此升到 `v02-gate` 15 场景 / 150 断言（含上述 F2/F3/F4、生命周期反例、覆盖率反例：未知第三方组件、缺 name、白名单外的插件、自带模型端点的随包组件）。

### 7.3 插件身份指纹的范围（独立复核后的修订）

第一版指纹只把包根下的 `.js` / `.mjs` / `.cjs` / `.json` 计入 `buildDigest`，这会漏掉
`dsh.bundle.patch` 指向的覆盖层：独立复核给了一个可复现的反例——`package.json` 声明
`dsh.bundle.patch: "./cordis.patch.yml"`，只修改这个 YAML，`buildDigest` 不变，核对仍然返回
`verified`。宿主真正加载的恰恰包含这一层，所以现在的口径是：

- **纳入**：包根下所有普通文件（跳过 `node_modules`、`.git`），按相对路径排序后
  `sha256(Σ"<文件 sha256>  <相对路径>\n")`；
- **入口**：`manifest.dsh.bundle.patch` 必须是非空字符串、不得是绝对路径、分段不得含 `..`，
  且必须命中已收集的文件；否则拒绝（`PLUGIN_IDENTITY_UNSUPPORTED_ENTRY`）；
- **符号链接**：包内任何符号链接一律拒绝（不跟随、不跳过），因为跟随会把指纹范围悄悄扩大到
  包外，跳过则会让"实际加载的内容"不在指纹里；
- **未覆盖**：peer 依赖与外部包、原生二进制在运行期的行为、profile 之外的 pnpm 副本
  （启动器会核对解析结果是否落在该 profile 根下，落在外面就判 `identity-unreadable`）。

登记表里的两个指纹都是**按这个口径从已安装包重算**的，不是照抄旧值：

| 包 | 版本 | 文件数 | buildDigest | bundle patch |
| --- | --- | --- | --- | --- |
| `tla-prelaunch-budget` | `0.0.0-local`（本地包） | 3 | `6fb8a042876ce78f7b3150f57172ff98a7ab823687ddb23ea0b7fd049b316477` | 无 |
| `@nanmicoder/dsh-agent-teams` | `0.1.23` | 123 | `e97e31807710852fd6ef45f433d91aaec174c183cd38d30bd305fb4d795eb29c` | `cordis.patch.yml` @ `699b8ba773693205db637a5fea7c0c9e38ce1668a148e347beb0ea4339c2079b` |

反例都在 `tests/v02-gate.test.mjs` 里：只改 YAML → `build-mismatch`；入口指向不存在的文件或
`../escape.yml` → `identity-unsupported`；包内符号链接 → `identity-unsupported`。

**这不是供应链认证。** 它只能证明"启动器核验的那些字节，和登记表里记录的字节一致"；它挡不住
本机管理员改文件后同时改登记表，也不覆盖 npm 分发链路本身。
