## 3. 三个可选方案

前提：`029bdcc` 是远端分支的当前 tip，且是本地 `HEAD` 的祖先。因此**任何以 `029bdcc` 为基线的发布分支，push 到同名分支都是 fast-forward**——不需要强推，也不会改写远端已有历史。

### 方案 R2（推荐）：无标识重放 + 快进发布

1. 以 `029bdcc` 为基线，把 43 个未推送提交**逐个重放**：对每个提交的树应用脱敏规则（只改命中文件），重算受影响的 `SHA256SUMS`/清单，保持提交信息与作者/时间不变。
2. 文档中对本地未推送 SHA 的引用改为**稳定标签**（提交主题 + 映射表），避免重放后出现悬空 SHA；`verify-run5.py` 的锚点命令改写为 `<delivery-commit>` 占位 + 解析说明。
3. 新增 `REDACTION-MAP.md`：逐提交 `旧 SHA → 新 SHA`、逐文件 `旧 sha256 → 新 sha256`、规则与验证方式。
4. 在本地新分支 `release/v0.1-public` 上完成，全部离线校验通过后，才把该分支**快进**推到 `feat/v0.1-three-agent-mvp`。
5. 原分支 `feat/v0.1-three-agent-mvp`（`[C43]`）保留为本地档案分支，改名 `archive/v0.1-verbatim`，**逐字原件只存在于本地**。

- 优点：保留运行叙事（run2 超预算、run3 中止、run4 中止、run5 干净通过各为其提交），审查者能逐提交读；fast-forward，无强推。
- 代价：43 个新 SHA；215 处 SHA 引用要处理；26 个文件字节改变，相关清单全部重算；脱敏副本不再等于逐字原件（必须显式声明）。

### 方案 R1（最省事）：压缩为单个发布提交

- 以 `029bdcc` 为基线，把 HEAD 的**整棵树**（脱敏后）压成一个提交 `feat: five-stage agent pipeline …`，再补一个说明提交。
- 优点：改动最少、最容易复核（一次 diff）；同样 fast-forward。
- 代价：失去逐提交叙事与失败轨迹的提交粒度；215 处 SHA 引用同样要处理（改成主题标签 + 映射表），所以省下的只是重放脚本，不是引用改写；审查者只能看到"最终状态"。

### 方案 R3（暴露面最小）：不发布 `docs/evidence/` 与 `docs/run-records/`

- 只发布代码、工作流、测试、需求/路线图文档；原始证据与运行记录只留本地，另附 `EVIDENCE-NOT-PUBLISHED.md` 说明"证据在所有者处，可按需提供"。
- 优点：**零哈希纠缠**（证据与其清单都不进公开树），公开树里没有任何本地路径/账户名；PR 体量从 206 文件降到约 40 文件。
- 代价：PR 里"可验证的运行证据"变成"摘要 + 本地证据"，说服力显著下降；`verify-run5.py` 的复算在公开树里无从对照。

**推荐 R2**：它同时满足"不公开本机标识""不改写远端历史""不把脱敏副本冒充原件"，并且保住项目最有价值的部分（可以逐提交读的真实运行轨迹）。R1 适合"只想尽快发布"；R3 适合"只发布可执行代码"。

## 4. 脱敏的具体影响

### 4.1 规则（拟定，可审）

| 原值 | 替换为 | 出现处 |
| --- | --- | --- |
| 工作区绝对路径（盘符前缀 + 仓库目录名；含反斜杠转义与正斜杠三种写法） | `<repo-root>` | 22 文件 / 125 处 |
| 本机用户主目录（反斜杠与正斜杠两种写法） | `<user-home>` | 2 文件 / 2 处 |
| 单独出现的本机账户名（路径片段内） | `<user>` | 1 文件 / 1 处 |

保留不动：`C:\tmp\…`、`C:\repo\…`、`C:\Windows\Temp`、`D:\Windows\Temp`——这些是文档里的**示意路径**，不含真实标识（若要求“公开树里不出现任何盘符路径”，需追加替换为 `<tmp>`，代价是示例可读性下降）。

### 4.2 对证据哈希的影响（必须明说）

- 26 个文件字节改变 ⇒ 它们自己的 `sha256` 全部改变。
- 覆盖这些文件的清单共 **11 个**（`EVIDENCE-MANIFEST.json`、7 个 `SHA256SUMS.txt`、`verification*.json` 等）⇒ 必须在同一提交内重算，否则公开树自相矛盾。
- **公开的 `preflight.json`、`commands.log`、`test-output/*.txt` 等是"脱敏重发副本"，不是工具当时写出的字节。** 逐字节原件只存在于本地档案分支；任何"本文件就是当时工具写出的字节"的表述在公开树里都不再成立，`REDACTION-MAP.md` 必须逐文件给出 `旧 sha256 → 新 sha256`。
- `workflow-script-at-run.js`（运行期脚本副本）不含这些标识，**不受影响**，其 `0099c08f…`（run5）等指纹仍可公开复算。

### 4.3 对固定提交引用的影响

- HEAD 里有 **215 处**对 43 个未推送提交短 SHA 的引用（其中 6 个提交从未被引用：`[C12]`、`[C13]`、`[C15]`、`[C23]`、`[C24]`、`[C43]`）。

### 4.4 对复核工具的影响

- `verify-run5.py` 的 28 项里，27 项按路径/内容判定，换到公开分支照常工作；**AC-29 依赖 `--base <交付提交>^` 与 `--delivery <交付提交>`**，重放后这两个 SHA 不存在。

  - a. 公开分支上把该命令写成 `--base <delivery>^ --delivery <delivery>`，由 `REDACTION-MAP.md` 查表填入；工具本身不改。

### 4.5 对 PR #2 更新的影响

- 现 head 是 `029bdcc`，发布分支以它为基线 ⇒ **fast-forward**，`git push origin release/v0.1-public:feat/v0.1-three-agent-mvp` 即可让 PR #2 自动带上新提交；**不需要强推、不产生 43 个旧 SHA 的远端垃圾**（它们从未上去过）。

## 5. 四条纠正（必须写进任何后续文档）

1. **"HEAD 级占位符提交"不能清除历史信息。** 在 HEAD 之上追加一个提交把账户名与工作区绝对路径换成占位符，只能让**新树**干净；那 43 个未推送提交里仍各自保存着原值，一旦推送就进入公开历史，且可被 `git log -S` 直接翻出。
2. **改写未推送提交 ≠ 改写已推送历史。** 本仓库这 43 个提交从未推送，重放它们不触碰远端任何对象，不需要 force push，也不影响 `029bdcc` 及其祖先。此前把两者混为一谈的说法（"改写历史会改掉 42 个 SHA"）只在"改写已推送部分"时成立。
3. **"无真实个人信息"的笼统结论不成立。** 准确表述是：无凭据/令牌/私钥/真实邮箱；但公开树里**有本机账户名 3 处与绝对工作目录路径 125 处**，这正是本方案要处理的对象。
4. **"预检必须逐字回报相对路径"已过期。** 现门禁是：相对路径逐字相等**或**绝对路径解算后指向同一文件（`ownerMarkerPathMatches`），提示词另钉死"逐字回填工具输出的相对路径、不要 `abspath`/`resolve`"。两者是"契约 + 容错"，不是"只认相对路径"。
