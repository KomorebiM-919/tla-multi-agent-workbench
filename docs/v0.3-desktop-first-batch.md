## 1. 交付范围

- 新增独立子工程 `desktop/`，仓库根 `package.json`（V0.2 observer 包）与冻结内核未改动。
- 中文 TLA 桌面窗口，暖白三栏布局：左侧项目导航（256px）／中间团队看板／右侧角色详情（344px）。

  新窗口一律 `deny`（不再调用 `shell.openExternal`），外部导航与 `<webview>` 挂载被阻止，全部权限申请被拒绝；

本批**没有**实现：聊天、智能分工、API 接入、自动替补、余额/用量、真实仓库读取、登录与审批流。

## 4. 启动验证：受限会话被阻塞，E 盘入口已由用户确认可打开

2026-11-04 用户反馈：E 盘入口 `<run-dir>\launch-tla.cmd` 能打开窗口，截图显示角色卡与对应详情——
入口本身可用。但这只覆盖“窗口能开、模板能看”，**不**代表完整 V0.3、原 `npm start` 或旧打包 `TLA.exe`
已通过验收；本节保留此前受限会话与目录层面的证据，避免把结论写过头。

### 4.1 受限会话内的失败证据（会话级限制）

在 DSH 受限会话里直接启动产物，Chromium 无法建立 mojo 通道，进程在创建窗口前退出：

```
FATAL:mojo\public\cpp\platform\platform_channel.cc:187] Check failed: . : 拒绝访问 (0x5)
ERROR:crashpad_client_win.cc:457] OpenProcess: 拒绝访问 (0x5)
```

同一现象出现在 Electron 45.2.1 与系统自带 Edge（`--headless=new`）上，属于会话级限制而不是本工程缺陷；
用诊断探针（只写日志的极简主进程）复现了同样的崩溃，进程在 `app ready` 之前以 `0xC0000005` 退出。

第二轮补充证据：带 `--enable-logging=stderr --v=1` 重定向 stdout/stderr 启动新包，两个日志文件都是 0 字节，
`%APPDATA%\TLA\logs` 与 `%TEMP%\TLA\logs` 均未生成——说明本会话里主进程脚本一行都没执行。
另外 `%APPDATA%` 下不存在 `tla-desktop` / `TLA` 用户数据目录，即本机（含两次桌面双击）从未创建过 Chromium profile，
这与“进程在 JS 之前就终止”一致；目录层面的原因见 §4.2。

因此本批**没有**完成“双击打包 exe 并截图”的验证，验收前不得声称“已实际启动”。

### 4.2 桌面双击无窗口：定位到原目录继承的 Low 完整性标签

2026-11-04 的 E 盘排查把“普通桌面双击也没有窗口”这条线单独定位了。`icacls` 证据：

- 原开发目录（C 盘旧仓库根）：`Everyone:(CI)(DENY)(DC)`、`S-1-4-…:(OI)(CI)(W,D,DC)`、
  `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`；
- 迁移出的运行目录 `<run-dir>`、`<run-dir>\runtime-45-normal`、`runtime-45-normal\electron.exe`：
  没有任何 `Mandatory Label` 行，即 `no-label`（普通 Medium）。运行目录用 `robocopy /COPY:DAT` 重建，
  只带数据/属性/时间，不复制安全描述符。

结论：启动故障定位为**原目录继承了 Low 完整性标签**，而不是 Electron 45 的兼容性问题——受限会话里
Electron 45.2.1 与系统自带 Edge 的表现一致（§4.1）。因此**撤回**“Electron 45 不兼容”的判断，
版本保留 45.2.1、不降级。

正常桌面入口随之改为运行目录里的 `<run-dir>\launch-tla.cmd`：它用运行目录自带的 Electron 45.2.1
（`runtime-45-normal\electron.exe`）加载 `<active-workspace>\desktop` 已构建的 `renderer-dist/`，
只清除子进程继承的 `ELECTRON_RUN_AS_NODE`、`TLA_DEV_SERVER_URL`，不改系统环境。
运行目录也不得再登记为 DSH 工作区，否则会被重新写入 ACL 与 Low 标签。

必须同时记住三条限制：

1. 这是“独立运行时 + 源码目录”的开发式启动，**不等于** `npm start` 或打包 `TLA.exe` 已永久修复；
2. 用户已在 2026-11-04 确认该入口能打开窗口并显示角色卡与详情；入口可用性已有反馈，但完整 V0.3 与打包路径
   仍**未验收**，不得写成“已全部验收”；
3. 权限/ACL 修复脚本本批不执行；后续权限再变化时，`PurgeAccessRules` 不能无条件当作
   “只删本次新增 ACE”的精确回滚，重跑前要先重新比对当时的 ACL 快照。

## 5. 无窗口问题：本轮做的修复

用户报告在普通桌面双击、以及清除 `ELECTRON_RUN_AS_NODE` 后用普通 PowerShell 启动，都没有窗口。
由于本机会话无法运行 Chromium，无法在这里复现真实桌面行为，本轮按“让失败可见 + 补齐可疑静默路径”处理：

1. **早期启动诊断**（`electron/diagnostics.mjs`）：在 `require('electron')` 之后立刻同步写日志，
   记录 `bootstrap`（版本、Electron/Chrome/Node、是否打包、页面、日志路径与可写性）、`single-instance-lock acquired=`、
   `app-ready`、`window-created`、`page-loaded`、`did-finish-load`、`window-shown reason=`、`did-fail-load`、
   `preload-error`、`render-process-gone`、`child-process-gone`、`uncaught-exception`、`unhandled-rejection`、
   `before-quit`、`quit`。单行、截断 300 字符、超 1 MB 轮转；写不进去不抛异常。日志不记录环境变量与凭据。
2. **窗口不再可能“静默不显示”**：显示触发条件从只有 `ready-to-show`，扩展为 `ready-to-show` / `did-finish-load` /
   2.5 秒兜底计时器三者取先；页面加载失败、preload 报错、`loadFile` 抛错、`whenReady` 拒绝、未捕获异常，
   都会把窗口显示出来并渲染一页中文错误说明（含时间、版本、页面、日志路径、详细原因）。
   如果失败发生在窗口创建之前，会补建一个 720×520 的窗口来显示这页说明。
3. **单实例锁不再静默**：拿不到锁时先写 `quit-secondary-instance` 再退出；被第二次启动唤起时，
   若已有窗口处于隐藏状态会 `show()` 出来，而不是只 `focus()`。
4. **构建脚本不再伪造成功**（`scripts/build-renderer.mjs`）：只有当沙箱确实拒绝 `spawnSync` 时才替换 `exec`，
   且只对已证实的 `net use` 探测返回可识别的失败；其他命令一律返回 `EPERM` 错误，不再用空输出冒充成功。
5. **边界收紧**：新窗口一律 `deny`、移除 `shell.openExternal`；`will-navigate` 与 IPC 均改用
   “精确页面 + 本窗口主 frame”判定（`electron/security.mjs`），开发服务器地址按完整 URL 比对。

这些改动都有单测覆盖（诊断格式与轮转、安全判定、启动步骤顺序、锁被占、加载失败错误页、2.5 秒兜底、日志回退、
whenReady 失败补窗），当时 29 个用例通过（追加本地项目/草稿后总数为 49）。修复**不能**保证解决所有环境下的无窗口问题：
如果进程在 JS 执行前就终止，应用内日志不会产生，需要看 Windows 事件查看器或 Chromium 自身的 stderr。
目录层面的根因另见 §4.2（原目录继承 Low 完整性标签），它比这些可见性修复更接近真正原因。

## 7. 本地项目与任务草稿（2026-11-04 追加）

在首批桌面壳之上增加本机多项目与任务草稿，不接模型、不读真实仓库：

- **存储**：新增 `electron/workspace-store.mjs`，固定写 `<workspace>\.local\tla-desktop\workspace.json`；
  结构 `{ schemaVersion: 1, activeProjectId, projects: [{ id, name, description, taskDraft }] }`，

  请求串行执行，失败保留旧数据。
- **IPC**：通道从 1 个扩到 3 个（`tla:app-info`、`tla:workspace-load`、`tla:workspace-save`），
  每个都绑定“本窗口主 frame 的精确应用页面”；预加载只新增 `loadWorkspace` / `saveWorkspace`，
  不暴露 `ipcRenderer`、任意文件读写或 shell。工作区路径由主进程按源码位置解析，不接受渲染层传入。
- **界面**：新建项目、编辑名称与简介、切换项目；每个项目独立任务草稿与保存按钮，状态显示
  “未保存 / 保存中 / 已保存（时间）/ 保存失败”。切换项目时未保存的修改留在本次会话，重开窗口回到最近一次成功保存的内容；
  保存只提交当前项目，不会顺带写入其他项目的未保存草稿。六个角色仍为只读模板。
- **结果**：`npm test` 49/49 通过（新增存储 11、编辑模型 7、IPC 边界 1，并更新既有 IPC/构建断言）；
  `npm run build:renderer` 通过，23 个模块、81 ms，`index.html` 0.79 kB、CSS 10.84 kB、JS 237.95 kB。
  本批没有重新打包，也没有在受限会话里启动 Electron；窗口内交互（保存、重开、切换读回）由用户按
  `desktop/README.md` 的验收步骤确认。
- `.local/` 与 `desktop/tests/.tmp/` 已加入 `.gitignore`；业务数据、测试临时目录、工具链与构建产物都不入库。

### 7.1 跨项目重叠保存修复（2026-11-04 追加）

- **问题**：保存 A 的请求还在途时切到 B 并保存，B 的 payload 仍按旧 baseline 构造，提交的是
  `A-old / B-new`；主进程虽然串行写入，仍会把 A 刚写入的更新覆盖回旧值。按钮只禁用当前项目，
  项目导航仍可切换，因此第二份过期快照能被提交。
- **修复**：新增 `src/lib/workspace-saver.js` 统一协调保存。它在第一次 `await` 之前同步置位 `inFlight`，
  在途期间任何保存请求直接返回 `busy`（不依赖按钮下一次渲染后的 `disabled`）；成功返回后再同步更新
  baseline，然后才释放保护。其他项目的保存按钮在途时禁用并提示“另一个项目正在保存”，切换与编辑不受影响。
- **测试**：新增 `tests/workspace-saver.test.mjs`，用受控 Promise 让保存挂起，覆盖 A 在途时 B 被拒、
  连点只提交一次、失败后释放可重试、保存期间继续编辑仍为未保存、B 的未保存草稿不被顺带写入也不丢失；
  先红后绿（红：2 个 `busy` 断言失败；绿：5/5）。全量 `npm test` 54/54，渲染构建 24 个模块、77 ms。

### 7.2 最近恢复稿与取消新建（2026-11-04 追加）

- **正式保存与恢复稿分离**：`workspace.json` 仍是显式保存的唯一正式数据；同一 `.local/tla-desktop/`
  新增 `recovery.json`，结构 `{ schemaVersion: 1, projects: [{ id, name, description, taskDraft, revision, updatedAt }] }`。
  每个项目只保留最新一份，编辑时按 400 ms 防抖备份；界面显示“备份中 / 已备份 / 备份失败”，
  与正式“已保存”分开显示。名称被清空的中间态也能备份正文；字段、ID、大小仍由主进程校验，
  超限报错而不截断。损坏、未知版本或超限的恢复稿原样保留并停止写入，不重置正式数据。
- **重开与放弃**：启动时并行读正式工作区与恢复稿；有恢复稿时提示“发现未保存内容”，逐个项目恢复或放弃。
  恢复只装入本次编辑会话，不自动覆盖 `workspace.json`；放弃只删该项目恢复稿。未处理的恢复稿跨多次重开保留。
- **顺序与身份**：新增 `electron/recovery-store.mjs`，写入用同目录临时文件 + `fsync` + `rename`，按项目串行；
  每条快照带单调递增 `revision`，磁盘上已有更高版本时拒绝（`STALE_SNAPSHOT`）；放弃/取消记录内存水位，
  迟到的低版本备份被拒（`DISCARDED`）。新增 `src/lib/recovery-drafts.js` 协调防抖、在途写入、关闭刷新与清理，
  定时器可注入，测试不需要生产延迟。

### 7.3 恢复稿审核修复（2026-11-05 追加）

- **REC-01 新建未保存项目可恢复**：恢复候选不再要求项目已存在于 `workspace.json`；恢复时把条目插入
  编辑会话并选中，仍保持“未正式保存”身份，不自动写正式文件。选择“稍后处理”只收起面板，候选不丢，
  可用提示条重新展开。
- **REC-02 清理后仍能继续备份**：清理已覆盖的恢复稿后不再销毁协调状态，而是保留 `revision` 水位；
  下一次编辑用更高版本写入，既继续受墓碑保护，也不会被旧水位误判为迟到请求。
- **REC-03 清理期间的新编辑不被删除**：清理只作用于捕获的快照；异步清理期间的新输入会重新防抖备份，
  返回 `{ cleared: false, reason: 'newer-edits' }`。`flush()` 只有最新内容确实落盘才报告成功，否则返回
  `RECOVERY_PENDING` 或真实错误。
- **REC-04 可取消最后一个未保存项目**：取消后显示可新建的空态，不自动创建替代项目、不写正式文件；
  保存中或刚好保存成功的项目不会被误取消，已保存项目仍没有取消入口。
- **REC-05 关闭超时有可操作反馈**：2 秒超时后主进程发 `tla:close-timeout`，界面提示“关闭前备份超时”
  并提供“返回继续编辑 / 仍然关闭”；每次关闭请求带单调 `requestId`，过期确认返回
  `STALE_CLOSE_REQUEST`，不会误关后续请求。
- **结果**：先红后绿（旧模块上 REC-01/02/05 三条断言失败，修复后通过）；`npm test` 86/86 通过，
  `npm run build:renderer` 25 个模块、76 ms，`index.html` 0.79 kB、CSS 13.73 kB、JS 252.95 kB。
  本批没有重新打包，也没有在受限会话里启动 Electron。

### 7.4 恢复稿并发与上限修复（2026-11-05 追加）

- **REC-03 清理纳入关闭刷新**：清理（`discard`）与备份进入同一项目的串行顺序，`revision` 不再并发分配；
  `flush()` 会等尚未返回的清理结束，再确认最新未保存内容已落盘，否则返回错误。原先清理不受
  `inFlight` / `pending` 跟踪，`flush()` 可能在清理挂起时提前返回，随后旧清理把新稿一起删掉。
- **REC-01 恢复遵守 20 项上限**：`mergeRecoveryEntry()` 已满 20 个项目时返回 `null`；界面明确提示、
  保留恢复候选、不改会话与正式文件；同 ID 的已有项目恢复不受上限影响。此前恢复可插入第 21 个，
  界面随即把候选标为已处理，正式保存却会被拒绝。
- **测试**：新增 `recovery-flow.test.mjs` 中“清理未返回时编辑并立即关闭”用例（真实 `recovery-store`
  + 受控 Promise 挂起 discard）与编辑模型中 19+1 / 20+1 用例。红：20+1 被静默接受；清理未返回时
  `flush()` 返回后最新恢复稿丢失（重读 0 条）。绿：`npm test` 88/88、`npm run build:renderer`
