## 2. 必须知道的两个风险

**风险 A：手机 UI 不区分"计划审批"与"宿主操作审批"。**

两者在页面上的唯一区别是 DOM 标记（`[data-question-key]` 与 `[data-plan-review-key]`），通知的 kind 也只有 `'done'` 和 `'question'`。也就是说，手机上的"批准"按钮长得一样——用户可能以为自己在批一个计划，实际批的是一个会改文件系统/装依赖的操作。

对策（未实现，属 V0.2 之后的工作）：在 TLA 侧给两类审批加不同的标题前缀或要求的确认词，让"手机上看起来不同"这件事由 TLA 自己保证，而不是指望插件的 UI。

**风险 B：除局域网外的连接方式都会把宿主暴露到公网。**

可选模式：LAN / Tailscale Funnel / cpolar / cloudflared / frp / 自建反代 / Caddy。除纯 LAN 之外，每一种都会让宿主从公网可达。结合"配对设备 = 完全可信操作员"，这等于把整个工作台（含审批能力）暴露出去。

对策：优先纯 LAN 或 Tailscale 私有网络；若必须公网，先明确"暴露多久、暴露什么、如何撤销"，并由用户单独批准。

## 3. 最短安装清单（待授权后执行）

1. 确认宿主版本与插件兼容表（当前宿主 `0.2.0-rc.2`，对应 track `legacy`）。
2. 下载 APK 0.6.5，核对 `sha256` 与上面的值一致；不一致就停止。
3. 在电脑端安装插件 0.6.11（安装命令以插件官方文档为准，本轮未核对、未执行）。
4. 只绑定内网地址启动，不配置任何隧道。
5. 手机扫码配对，密钥一次性使用，不截图、不外传。
6. 立刻做三件事验证：
   - 在手机上看一次**只读**进度（例如当前会话的日志）；
   - 发起一次**故意不批准**的审批，确认电脑端能看到"被拒绝"，而不是"超时"；
   - 在电脑端撤销该设备，确认手机端会话被 `device-revoked` 断开。
7. 记录安装时间、插件版本、APK 校验值、绑定地址、配对设备名，作为本机验收证据（不进仓库）。

## 4. 回滚清单（必须能一步撤回）

1. 先在电脑端撤销配对记录（不要只在手机上删行）。
2. 卸载/禁用插件。
3. **注意**：移除插件会留下 `$DSH_HOME/mobile-access/` 下的证书与配对记录；彻底清除需要执行 `dsh plugin --profile web exec dsh-mobile purge --yes`。
4. 关闭隧道/端口转发（如果开过）。
5. 重启宿主，确认 Web UI 不再显示移动端入口。
6. 记录回滚时间与结果。

## 5. 本轮未做的事

- 未安装插件、未安装 APK、未重启宿主、未开放端口、未配置隧道。
- 未调用任何模型，未读取任何凭据。
- 未把手机上看到的任何界面当作"已验证可用"——真实的手机内核、移动网络与公网线路都还没测过，这需要用户亲自安装、扫码并在移动网络下完成一次审批实测。
